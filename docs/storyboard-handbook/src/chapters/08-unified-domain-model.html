第八章 · Canonical Domain Model

先保存创作决定，再编译供应商格式

重构建议 这一章提出一套供应商无关的规范模型。它不是 Narrative Forge 或 shuohao-skills 已经实现的 schema，而是一张可供重写、迁移和长期演进的设计底图：故事事实、导演决定、生产任务和具体文件各有自己的身份。系统默认编译的提示词是可重建的 derived Artifact；人工改写后，它就成为有来源记录的 authored override。

六条不变量，比字段数量更重要

重构建议 先把系统必须长期守住的关系写成不变量，再决定用 TypeScript、Python、SQLite 或别的技术实现。否则，即使对象名看起来专业，同一项决定仍会在提示词、页面状态和导出文件之间产生三份互不相认的真相。

  1. 身份稳定：业务实体获得不可变 ID；标题、顺序和文件名变化时，引用不随之改变。
  2. 层级不混：故事图、集、戏剧场次、节拍、镜头、画格、生成段和执行任务分别建模。
  3. 决定可溯：人工撰写、人工覆盖、规则派生和模型生成都记录来源及输入版本。
  4. 关系可多对多：一个 beat 可以被主镜、反应镜和插入镜共同覆盖；一个 shot 也可以承担多个 beats。
  5. 分支可汇流：选择边不仅指向节点，还描述条件、状态补丁和 join 前必须满足的兼容规则。
  6. 批准绑定版本：“已批准”指向精确 revision；上游改变后，受影响的派生产物会过期，而不是继续冒充最新版。

分析推论 更细的模型会增加录入和迁移成本；它的收益只在修改、重跑、审阅、协作或更换供应商时兑现。因此应让简单项目使用合理默认值，而不能为了表面简洁再次合并概念。

关系图：四条链共享 ID，不共享职责

实体词典：每个名字只承担一种责任

Project作品身份、形式契约、默认语言和当前发布指针。拥有 StoryGraph、Episode、Asset。浏览器临时选择、API key。

DramaticScene一次具体场次的目标、阻碍、转折、地点和在场者。属于 Episode，拥有 Beat。可复用地点资产本身。
Beat动作、台词、反应、揭示或决定造成的状态变化。属于 DramaticScene，经 link 被 Shot 覆盖。数组位置或固定秒数。
Shot观看功能、机位、构图、运动、声音、估时和状态边界。多对多覆盖 Beat，拥有 Panel。具体模型请求与生成文件。
Panel镜头内某个关键时刻的构图、姿态、视线和注记。属于 Shot，可引用参考 Asset。有文件身份的最终关键帧。
ContinuityState边界时刻的人物、道具、空间、光线、声音与知识状态。附着于场次、beat 或 shot 的 entry／exit。只有“保持一致”的自然语言愿望。
Asset角色、地点、道具、风格或参考物的逻辑身份与批准版本。被 DramaticScene、Shot、Panel 引用。一次任务的临时 URL。
GenerationSegment一次计划生成的连续时间单元、shot 顺序和时长预算。引用一个或多个 Shot，派生任务。戏剧场次身份。
CanonicalSnapshot某次编译、执行或发布所见的不可变 id@revision 闭包。从稳定 ID 解析可达实体，被 Approval、Task 和 Release 引用。正在编辑的草稿指针。
GenerationTask已批准 snapshot ref、adapter、参数、依赖、状态、尝试和幂等键。消费 CanonicalSnapshot 中 segment、shot、asset 等全部精确 revisions，产出 Artifact。需要长期编辑的创作事实。
Artifact提示、图像、视频、音频、字幕、报告或清单的不可变文件身份。由任务或编译器产生，可晋升为 Asset revision。可重试的任务状态。
ProviderAdapter能力声明、协议版本、编译和结果归一规则。被 GenerationTask 按版本引用。密钥值和领域事实。
MigrationRecord原始 Artifact、旧类型／ID／顺序／关系与候选映射。只属于 migration-staging，人工或明确规则晋升后才产生规范实体。已被确认的创作事实。
Provenance输入 revision、规则／模型／人工动作与输出之间的有向边。横跨所有实体和 Artifact。只有时间戳的一行日志。

重构建议 ShotBeatLink 应是有 ID 的关系记录，而非藏在两边的 ID 数组；它至少保存 role、coverageWeight 和 order。这样主镜、反应镜、插入镜以及一个长镜覆盖多个 beats 都能被显式表达。

草稿、快照与迁移隔离区不是同一层

重构建议 作者编辑时，关系指向稳定 ID，写入通过 expectedRevision 防冲突；到编译、执行或发布边界，系统才把全部可达 ID 解析为 CanonicalSnapshot 里的精确 revisions。这既避免草稿关系过度繁琐，也防止一次任务在途中消费新修改。

重构建议 无法无损对应 DramaticScene、Beat 或 StoryGraph 节点的旧记录进入 MigrationRecord，而不是放宽规范模型的“无孤儿”不变量。隔离记录可审阅、可重跑，但不得被批准、生成或发布；晋升动作必须创建完整规范关系并写入 provenance。

Authored 与 derived：可编辑不等于都是源事实

重构建议 表 2　写作事实、导演决定和机器派生的处理方式
类别例子保存规则上游改变后
authored场次目标、beat 内容、镜头功能、人工指定时长。作为实体 revision 保存；修改必须说明基于哪个 revision。产生新 revision，不静默覆盖旧决定。
approved override导演改写模型给出的构图或对白。仍是 authored，并以 provenance 指向被覆盖的建议。除非人工撤销，重新生成不能覆盖。
derived供应商提示词、切点 manifest、缩略图、TTS 估时。保存为 Artifact，记录 compiler、输入哈希和参数。标记 stale，可重编译但不自动冒充已批准。
observed视频真实时长、分辨率、模型 job ID、文件哈希。从执行结果采集，写入 Artifact／Task 事实。不可编辑；新执行产生新记录。

分析推论 允许编辑派生提示词是合理的人机协作需求，但一旦人工改动，它就应被晋升为带来源的 authored override。继续把它叫“自动生成字段”，会让下一次重编译不知道该覆盖还是保留。

分支汇流、版本和人工批准必须说清“哪一个”

分支不是树形文件夹

重构建议 每条 edge 保存版本化的声明式条件与 statePatch；条件由白名单谓词解释，绝不把字符串交给 eval。join 节点声明必须相等、允许并集或需要人工选择的状态字段，验证器对所有入边求兼容性。

版本不是一个全局数字

重构建议 每个实体维护 append-only revision、baseRevision 与内容哈希；项目的 schemaVersion 只说明格式，不说明某一镜头是否最新。

批准不是布尔值

重构建议 Approval 保存对象 ID、revision、批准范围、批准人和时间。上游 revision 改变后，影响分析把相关批准标为 superseded 或 needs-review。

重构建议 写 API 时要求客户端提交 expectedRevision；不一致就返回冲突和最小 diff。生成任务只接受已批准 revision 的不可变快照，因此一次失败重试不会意外消费用户刚改到一半的页面状态。

本章结论

重构建议 规范模型的核心不是多建几张表，而是把不可逆的创作决定从供应商格式中解放出来。稳定 ID 保护身份，多对多 link 保护覆盖意图，revision 与 Approval 保护人工决定，Provenance 保护可解释性，ProviderAdapter 则让提示词、请求和文件布局保持可替换。

重构建议 本章全部领域结构均为本手册提案，不是两个仓库的现状。问题来源基于 Narrative Forge 24c3c47 的项目／镜头／任务实现与 shuohao-skills 4322897 的阶段 JSON、位置索引和质量门；现状证据与具体路径见第三至第七章及 SOURCES.md。
