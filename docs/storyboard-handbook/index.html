导读 · 阅读地图

先学会区分事实、方法与建议

这不是一本教你照着某个界面点击的说明书，而是一份可以反向拆解第三方系统、再正向设计自己系统的学习地图。你会同时接触影视语言、结构化数据、生成模型约束和两个仓库的具体实现。它们彼此有关，却不是同一层的问题。

完整学习版的范围

本版共 11 章：导读、共同基础、一个贯穿案例、Narrative Forge 两章、shuohao-skills 两章、比较与重构三章，以及最终随身参考。它会把两套仓库的冻结证据对象追到字段、调用、校验与导出层；Narrative Forge 还分别保留上游快照、公开 fork 与本地基线的归因边界。手册不会把未公开的镜头配方卡、未实际调用的第三方模型，或本书提出的未来模型伪装成已验证的仓库能力。

Narrative Forge 提示词专题

如果你希望逐字段观察“默认值／用户输入 → 请求体 → system/user prompt → 模型响应 → 解析与安装 → 分镜列表”，可另开独立的交互式 Prompt Pipeline Lab。它绑定同一套源码证据，但不把教学响应冒充真实模型运行。

这本手册怎样回答问题

每当看到一项设计，先问四遍“为什么”：故事为什么需要这一步？观众为什么需要这个镜头？生产为什么需要这个字段？程序为什么需要把它保存下来？只有四个答案能彼此对上，这项设计才真正进入了系统，而不只是提示词里的一句话。

贯穿全书的原则

故事事实、导演选择和供应商参数必须分层。“弟弟被困在核心旁的维修救生舱”是故事事实；“用吊臂俯拍表现她的孤立”是导演选择；“生成 5 秒、使用首尾帧约束”是某次生产任务的参数。把三者塞进同一个字符串，短期方便，长期几乎无法验证、改写或迁移。

证据标签：一句话究竟从哪里来

分析第三方项目时，最危险的错误是把“作者说它会做什么”直接当成“代码实际做了什么”，或把“一个测试通过”误当成“创作质量已经得到证明”。本书用以下标签把证据层级明示出来。

通用方法
影视制作、叙事设计或软件建模中的通用概念。它用于建立比较坐标，不表示所有项目都必须采用同一术语。
文档声明
README、使用说明或作者注释表达的意图。它能解释“想做什么”，但仍需与源码和产物互证。
源码实现
在固定提交中能沿调用关系、数据读写和分支条件定位的行为。它回答“现在实际上怎么做”。
测试约束
自动化测试明确保护的输入、输出或失败条件。测试只能证明覆盖到的契约，不能自动证明镜头好看。
运行验证
在注明环境、配置和步骤后观察到的结果。它比截图更有价值，因为别人可以重复验证。
分析推论
依据前述证据得出的解释、风险或权衡。推论会写出依据，不伪装成作者原意。
重构建议
面向未来系统提出的领域模型、流程或接口方案。它可能优于现状，但不是对现有仓库行为的描述。
月城案例
为教学原创的虚构材料，用来让同一概念在文字、图像和数据之间来回映射，不属于任一第三方仓库。

若一段话同时包含两类证据，本书会拆开写。例如：“README 把分镜描述为最终环节”属于文档声明；“对应脚本只读取已完成剧本”属于源码实现；“因此它试图禁止分镜阶段改写剧情”才是分析推论。

四条阅读路径

第一次系统学习分镜

  1. 先读本章和“共同基础”，把层级与术语分开。
  2. 跟随《月城失物局》完成一次从梗概到故事板的全过程。
  3. 再读两个仓库的解剖，观察它们在哪里合并或省略了步骤。
  4. 最后读重构篇，理解数据模型为何这样划分。

  1. 读完术语分层后直接进入 Narrative Forge 篇。
  2. 把界面里的“场景”逐项映射到故事节点、镜头和地点资产。
  3. 回到共同基础，补齐系统当前没有持久化的中间层。
  4. 用重构篇判断渐进改造和重新实现的边界。

准备编程重写

  1. 重点阅读“来源事实与派生字段”“稳定 ID”和“多对多关系”。
  2. 对照两个仓库的数据契约、提示词契约和校验边界。
  3. 先建立供应商无关的核心模型，再设计模型适配器。
  4. 把每个生成步骤变成可保存、可复现、可人工修改的阶段。

只关心 AI 视频投产

  1. 仍需先读场次、节拍和镜头覆盖，避免用提示词替代导演设计。
  2. 重点阅读关键帧、连续性、生成段和投产包。
  3. 把特定模型的时长、参考图和提示格式视为适配层约束。
  4. 用 animatic 先验证节奏，再投入昂贵的生成与返工。

先建立三套坐标，不要把所有东西都叫“场景”

一部影像作品至少同时存在三种粒度。叙事层描述发生了什么；导演层描述观众怎样看见；生产层描述机器或团队怎样把它做出来。它们会相互引用，但不能互相替代。

表 1　本手册的分镜核心术语与边界
术语 本书中的工作定义 最容易混淆的对象
场（scene） 在一段相对连续的时空和行动中完成一个戏剧任务的叙事单位。 地点资产。控制室可以反复出现于多场戏，它不是“那一场戏”本身。
节拍（beat） 让行动、信息、情绪、关系或决定发生一次可辨认变化的最小叙事单位。 句子或固定秒数。一个节拍可以无台词，也不由标点决定。

本书如何使用“分镜列表”这个词

中文语境中的“分镜”常同时指文字镜头表、故事板图和镜头设计行为。为了减少歧义，本书在需要精确时使用三个词：

  • 镜头列表：逐镜头的结构化文字规格，重点是覆盖什么、为什么这样看、如何衔接。
  • 故事板：与镜头编号对应的视觉面板，重点是构图、调度、方向和关键状态。
  • 分镜列表：连接两者的上位交付物；每个镜头既有文字记录，也能关联零到多个面板、音频和生产任务。
月城案例

“阮星发现母亲的求救信号仍在城市核心中循环”是故事事实。镜头列表可以决定先给控制室全景，再给屏幕特写，最后切阮星反应；故事板画出她与屏幕的位置关系；投产任务则指定参考图、时长和生成模型。四句话说的是同一时刻，却属于四种不同数据。

给未来程序员的两个关键概念

来源事实与派生结果

通用方法 若镜头时长可以由时间线计算，就不应在多个地方各存一份互相矛盾的数值；若模型提示词可以由镜头规格和资产引用编译得到，它就应被视为可再生成的派生结果。真正需要长期保存的是创作者作出的决定、来源引用、人工覆盖和生成版本。

有损转换与可追踪关系

重构建议 从梗概到镜头不是“换一种格式”，而是连续作出新决定。每往下一层，内容更具体，也更难从结果倒推出原意。因此应为集、场、节拍、镜头和资产建立稳定 ID，并保存它们之间的引用关系。这样才能回答：这个特写在服务哪个节拍？删掉这句台词后，哪些镜头和提示词需要重算？

读完本章，你应当能做到

  • 看到一项结论时，先判断它是声明、实现、测试、实测、推论还是建议。
  • 不再把场次、地点、镜头、画格、生成段和媒体片段混成一种对象。
  • 理解“分镜列表”是从故事语义通向视觉执行的桥，而不是一串华丽提示词。
  • 在阅读代码时主动寻找稳定 ID、来源引用、派生字段和人工覆盖点。

第一章 · 共同基础

从粗梗概到可执行分镜

分镜不是把梗概切成若干句，再给每句补一个景别。它是一条逐层作决定的链：先确定观众将经历什么，再确定每一场戏怎样改变局面，然后才决定观众从哪里、以什么节奏看见这些变化。本章先建立这条共同链路；后续再比较两个仓库在哪些层完整建模，哪些层交给模型暗中完成。

先看全程：九个产物，八次交接

每次交接都应回答三件事：上游有哪些事实不能被下游擅自改变？下游被授权作哪些新决定？用什么检查发现它越权或漏项？这三个问题也正是未来编程实现的接口契约。

第一步：把粗梗概变成可工作的故事简报

粗梗概不是缩短版剧本。它的职责是交代故事发动机：谁在追求什么，什么力量阻止他，失败要付出什么代价，以及经历迫使他发生什么变化。细节不足并不可怕；真正危险的是把尚未决定的内容写得像既定事实。

表 1　把粗梗概整理成可执行故事简报的六项检查
检查项 要回答的问题 暂时答不出时怎样记录
主角与视角 观众主要跟随谁？谁承担选择的后果？ 标记“待决定”，不要让生成模型随意更换主角。
显性目标 主角在故事结束前具体想完成什么？ 先写成可验证的行动目标，而不是“寻找自我”一类主题词。
阻碍与对抗 谁或什么持续让目标变难？阻碍如何升级？ 区分外部阻碍、关系阻碍和内部矛盾。
代价与时限 失败会失去什么？为什么不能以后再处理？ 若没有倒计时，也要有不可逆的机会窗口。
核心变化 结尾相对开头，人物、关系或世界发生了什么不可忽略的变化？ 把多个可能结局列为候选，而不是过早混成一个结局。
世界规则 哪些设定会限制人物行动和视觉表现？ 记录规则、例外和代价，不急着扩写百科。
月城案例

月城将在日出时永久断电。维修学徒阮星发现，失踪母亲留下的求救信号仍在城市记忆核心中循环。她必须在一小时内决定：恢复整座城市的记忆，还是关闭核心救出被困的弟弟。

这个梗概已经给出主角、倒计时、两难选择和代价，但仍缺少母亲为何失踪、信号为何留在核心、弟弟为何被困在核心区的救生舱、两种选择是否真的互斥等因果。下一层可以提出并解决这些问题；不能假装它们已在原文中得到回答。

程序设计提示：保留“已知”与“待定”

建议把来源明确的事实、创作者后来批准的补充、尚未解决的问题分别保存。若只保留一段不断被重写的梗概，就无法判断模型究竟是在展开原意，还是偷偷修补了它自己制造的漏洞。

第二步：先定形式契约，再谈镜头数量

同一个故事做成九十秒线性短片、三集竖屏短剧和互动影游，信息出现的顺序、悬念位置和可接受的镜头密度都会改变。形式契约是创作任务的边界，不是某个视频供应商的参数表。

观看结构
线性、分集线性、带选择的分支，还是允许分支重新汇流的状态图？
时长与节奏
总时长、每集目标时长、开场多久必须建立问题、结尾是否需要钩子。
画面载体
横屏、竖屏或可适配；主要观看距离；字幕和界面需要预留的安全区域。
互动规则
选择点数量、可见选项、隐性状态、失败状态、是否允许回看与汇流。
生产方式
实拍、动画、AI 视频或混合；哪些角色、地点和动作受到现实或生成能力限制。
交付标准
只需概念预演，还是必须交付可剪辑片段、配音对齐、字幕、音效和版本记录。

不要过早把模型限制写进故事

“某供应商一次最多生成若干秒”属于生产适配约束；“这一场只能发生若干秒”属于叙事决定。可以让生产层把长镜头拆成多个任务，但不能反过来让接口上限决定人物何时改变主意。

同一梗概，两种形式契约

线性版：观众跟随阮星调查，最终看见她作出唯一决定。结构需要让这个决定既意外又有充分铺垫。

互动版：观众在信息充分但后果未完全显露时替她选择。选择前必须建立清晰价值冲突；选择后每条分支都要兑现不同代价，不能只换最后一句台词。

第三步：搭建全局结构，而不是套一个万能公式

三幕、起承转合、序列法或节拍表都可以作为检查视角，但结构的本质是因果安排：上一事件怎样迫使下一事件发生，人物每次行动怎样改变可选项，前面建立的信息怎样在后面兑现。模板能提醒你遗漏，不能替你生成因果。

一份可用的结构图至少标出

  • 开场承诺：观众最早会对什么问题产生兴趣。
  • 触发事件：原有平衡为何不再能维持。
  • 升级链：阻碍怎样因为人物的行动而升级，而非随机叠加。
  • 关键转折：新信息或不可逆选择怎样改变目标、方法或代价。
  • 铺垫与兑现：一个物件、规则或关系何时建立，何时发挥作用。
  • 高潮决定：主角必须做什么，才能证明他已经改变或拒绝改变。
  • 结局状态：外部问题、人物关系和主题问题分别落在哪里。

互动结构多一步：先画状态图

互动故事应在分镜之前定义节点、选择条件、状态变化、分支进入条件、失败或结局条件，以及允许汇流时必须保持的共同事实。摄影机不应负责决定剧情图。否则一个看似简单的镜头改动可能意外创造新的结局状态。

第四步：把全局变化分配给每一集

分集不是按字数把梗概平均切开。一集应有自己的进入状态、即时目标、主要问题、至少一次局面变化和明确退出状态；系列级悬念与本集级满足需要同时存在。

月城案例 下表不是原梗概中已经存在的事实，而是本手册为了继续推演而批准的补充假设：调查开始时，阮星相信母亲已经死亡；本集会动摇这项信念。

本集问题 这一集承诺回答或显著推进的问题。 循环信号是谁发出的？

退出状态 本集结束后不可假装没有发生的变化。 阮星确认母亲的意识可能仍在核心中。
结尾钩子 让下一步行动不可回避，而不是故意藏掉正常信息。 屏幕同时弹出弟弟的生命维持倒计时。

单集短片也需要同样的逻辑，只是“分集方案”和“全局结构”可能合并为一张结构卡。可以合并工作步骤，但不要丢失进入状态、退出变化和时长预算这些职责。

第五步：把每一集拆成有任务的场

一场戏通常维持相对连续的时间、地点和行动线，并完成一个戏剧任务。换地点往往意味着换场，但“同一地点”不等于“同一场”：角色离开数小时后回到控制室，地点资产相同，戏剧场次已经改变。

场次卡应回答

  • 场号和来源：它属于哪一集、承接哪个结构事件。
  • 时间与地点：不仅用于美术，也决定光线、声音和连续性。
  • 在场人物与入口状态：谁知道什么，谁携带什么，关系处于何种张力。
  • 场次目标：焦点人物在这场具体想取得什么。
  • 阻碍与策略：为什么不能直接取得，他先后尝试了什么。
  • 转折和退出状态：局面发生了什么变化，下一场为何必须发生。
  • 连续性负债：位置、服装、损伤、道具、时间和未兑现信息有哪些必须带出去。
月城案例 · 场 SC-03

地点／时间：地下控制室，断电前 42 分钟。

目标：阮星要绕过权限，确认信号源。

阻碍：系统要求母亲的实体密钥；巡检无人机正在接近。

转折：她发现自己项坠中的旧螺母就是密钥外壳。

退出状态：核心解锁，但弟弟的生命读数同时出现。

场次表还不是镜头表

“地下控制室，夜；阮星打开核心”只规定戏发生在哪里、发生什么，没有规定用远景、特写还是长镜头。保留这层独立性，才能在不改剧情的情况下比较两种导演方案。

第六步：把场拆成可观察的节拍

节拍是叙事变化，不是排版单位。一个动作、一次停顿、一句台词或一个声音都可能形成节拍，前提是它改变了行动、信息、情绪、关系或决定。若删掉某行后场面的状态完全不变，它多半只是动作细节；若一行同时完成三次重要变化，它又可能需要继续拆分。

  1. B03-01 控制室门在阮星身后自动锁死。空间与危险变化
  2. B03-02 屏幕亮起：“剩余 42:00”。时间压力被看见
  3. B03-03 循环噪声中出现三短一长的维修音。新信息进入
  4. B03-04 阮星认出母亲教过她的暗号，停止拔线。认知与行动同时改变
  5. B03-05 她把项坠按上读取槽，核心解锁。策略奏效
  6. B03-06 弟弟的生命读数覆盖母亲信号。目标发生冲突

节拍表需要保留什么

至少保留稳定编号、类型、发生的可观察事实、涉及人物或资产、承接的状态变化、原始台词或声音，以及必要的时长依据。台词字数可以帮助估时，但不能替代朗读和表演；动作时长也应通过预演修正，而不是由模型凭印象给出一个精确数字。

节拍与镜头是多对多关系

一个长镜头可以连续承载门锁、倒计时和阮星走向屏幕等多个节拍；同一个“屏幕亮起倒计时”节拍也可以先在建立全景中出现，再由屏幕插入特写强调。数据模型若强迫每个节拍只能归属一个镜头，会让重叠覆盖、反应镜头和多机位设计难以准确表达。

第七步：先决定观看功能，再选择景别和运镜

设计镜头时最先问的不是“这里用什么酷炫运镜”，而是“此刻观众必须看懂什么、感到什么、暂时不能看见什么”。然后依次决定主体、空间关系、信息优先级、景别、角度、构图、运动和持续时间。

  1. 叙事功能：建立空间、揭示信息、观察反应、强调物件、制造遮蔽或完成转场。
  2. 观看对象：这一刻最重要的是人物、动作、环境、界面还是另一人的反应。
  3. 空间与连续性：观众是否知道人物在哪里、看向哪里、朝哪个方向移动。
  4. 镜头尺度与角度：景别控制信息范围，角度影响权力感和可见关系。
  5. 摄影机行为：固定、跟随、摇移、推拉等动作是否由场面变化触发。
  6. 时间与声音：镜头要容纳多少动作、台词、停顿和声音先行或延续。

完整镜头记录通常需要的字段

  • 身份与来源：镜头 ID、版本、所属集与场、覆盖的节拍引用。
  • 导演意图：镜头功能、观众应获得的信息或感受、可接受的替代方案。
  • 画面规格：主体动作、景别、角度、构图、摄影机运动、人物调度、屏幕方向。
  • 时间和声音：估计时长、台词、环境声、音效、音乐、声音先行或延续。
  • 连续性：人物位置、视线、道具状态、服装损伤、光线和前后镜头衔接。
  • 生产引用：角色、地点、道具和参考资产的稳定 ID，以及对应任务和结果。

镜头列表可以按叙事顺序阅读，也可以在生产时按地点、光线、演员或资产组合重新编组。镜号表达最终剪辑中的位置；生产批次表达如何高效生成或拍摄。两种顺序不要混用同一个字段。

第八步之一：故事板把文字中隐藏的空间问题画出来

故事板不是镜头列表的装饰图。草图的价值在于暴露文字很容易掩盖的问题：人物究竟站在哪里，谁在看谁，关键道具是否被遮挡，前后镜头的运动方向是否一致，竖屏安全区里还能否同时容纳两个人。

一个镜头需要几幅面板

固定构图、动作简单的镜头可能一幅就够；人物走位、摄影机运动、揭示关系或变形明显时，需要起始、关键转折和结束面板。面板数量由需要验证的变化决定，不必机械规定“一镜一图”。

彩色完成画面放在哪里最有价值

彩色关键帧适合验证角色外观、材质、光色、关键地点和高风险特效，不必覆盖每个普通正反打。先用草图确认戏和空间，待设计稳定后再把少量代表镜头提升为完成画面，返工成本最低。

第八步之二：animatic 把故事板放回时间里

Animatic 是按预计时长排列的故事板预演，通常加入临时对白、音效或音乐。它不要求最终画质，目标是让人真实经历一次节奏：信息是否来得及读懂，停顿是否成立，对白与动作是否互相挤压，转折是否太晚，结尾钩子是否有足够重量。

Animatic 与故事板的反馈关系

  • 信息读不清：可能需要延长插入镜头、简化画面或把信息提前建立。
  • 对白太密：先检查台词和节拍是否重复，再考虑增加镜头时长。
  • 情绪不成立：检查反应是否缺失、前因是否不足，而非盲目加慢动作。
  • 空间混乱：回到场面调度和故事板，补建立镜头或修正视线方向。
  • 总时长超标：优先删除不改变状态的节拍和重复覆盖，再压缩表演时间。

第九步：把已批准的分镜编译为投产包

投产包的任务是让另一个人或另一套程序在尽量少猜测的情况下执行分镜。它不应偷偷新增剧情决定。对于 AI 视频，最好先维护供应商无关的镜头规格，再由适配器编译出特定模型需要的提示词、参考图槽位、时长和请求参数。

通用镜头规格

  • 镜头与节拍的来源关系
  • 主体动作、构图、机位、运动和声音意图
  • 人物、地点、道具及其当前状态
  • 时长范围、前后衔接和必须保持的连续性
  • 故事板面板、首尾关键状态和人工备注

模型适配结果

  • 按供应商格式编译的提示词
  • 可接受的参考图数量与具体槽位
  • 模型、分辨率、比例、时长和可选参数
  • 首帧、尾帧或多图时间对齐表达
  • 接口请求、重试规则和结果解析

生产清单与追踪

  • 任务 ID、依赖关系、批次与优先级
  • 输入资产版本、生成参数和随机性记录
  • 执行状态、错误、候选结果和人工选择
  • 授权、来源、文件校验值和输出路径
  • 质量检查、批准者与进入剪辑的版本

提示词不是系统的唯一真相

提示词适合传递给模型，却不适合承担全部领域数据。人物 ID、道具状态、节拍来源和镜头衔接若只存在于自然语言里，程序很难可靠检查，也无法在更换供应商后重新编译。

自动化最适合保护可明确陈述的契约；它不能替代“这个镜头为什么在这里”的判断。反过来，审美判断也不能成为漏 ID、丢台词或时长算错的借口。

把整条流程写成可编程的交接契约

  1. 梗概 → 结构：保留来源事实；允许补足因果候选；必须标记新增假设并等待批准。
  2. 结构 → 分集：保留关键事件与铺垫兑现；允许分配节奏；不得删除核心选择而不留变更记录。
  3. 分集 → 场次：保留进入退出状态；允许选择地点和冲突策略；必须能追溯每场的结构功能。
  4. 场次 → 节拍：保留场目标和转折；允许具体化动作、台词与反应；必须控制表演与时长预算。
  5. 节拍 → 镜头：保留可观察事件；允许设计覆盖；必须说明节拍与镜头之间的关系。
  6. 镜头 → 故事板：保留镜头意图和连续性；允许具体化构图；必须标出运动和关键状态。
  7. 故事板 → animatic：保留顺序和对白；允许调整时长；任何删改镜头都应回写镜头版本。
  8. 分镜 → 投产包：保留通用规格；允许按模型编译；供应商限制不得无记录地反向改写故事。

本章结论

分镜列表的输入不是一段等待切割的文字，而是一组已经获得批准、仍可追溯的故事决定；它的输出也不是提示词，而是一套说明观众怎样看见故事、生产系统怎样执行这些选择的镜头规格。镜头列表、故事板和 animatic 分别保存文字、空间和时间证据，投产包再把它们编译成可执行任务。

  • 任何镜头都能回答“它覆盖哪个节拍、承担什么观看功能”。
  • 任何节拍都能找到镜头覆盖，必要时允许被多个镜头共同表现。
  • 场次与地点资产、镜头与故事板画格、镜头规格与生成结果不再混淆。
  • 供应商提示词可以重新生成，创作决定和人工覆盖则被长期保存。
  • 自动检查保护结构契约，animatic 和人工评审负责判断节奏与表达。

完整样章 · 从场次任务到可生成分镜

月城控制室：一场戏如何变成八个镜头

分镜不是把文字平均切成八段，而是决定观众依次看见什么、何时理解、何时犹豫。本章用同一场戏走完“场次任务 → 节拍 → 镜头 → 故事板 → 程序数据”的完整链路。

读完本章，你应该能判断三件事

  • 一个镜头为什么存在：它认领了哪个叙事节拍，又让观众获得了什么新信息。
  • 相邻镜头为什么能接上：人物、视线、道具、光线与动作状态如何交接。
  • 同一套导演设计进入不同程序时，哪些信息被保留、压扁、改写或丢失。

一、先锁定故事契约，不要急着想镜头

我们的原创故事暂名《月城失物局》。月城将在日出时永久断电。维修学徒阮星追踪到母亲留下的求救信号，却发现信号藏在城市记忆核心中；与此同时，她的弟弟被困在核心旁的维修救生舱。最后一组备用电容只能完成一件事：把全城居民的记忆写回他们体内，或打开救生舱救出弟弟。

这是全剧层面的困境，还不是一场可拍的戏。分镜前必须先把它收敛成一个有明确起点、变化和终点的场次。

故事事实

断电即将发生；母亲的信号、城市记忆核心和弟弟的救生舱都真实存在。

场次任务

让阮星亲眼确认“两件事不能同时完成”，把抽象道德难题变成一个必须立刻按下的物理选择。

镜头任务

逐步交付空间、亲情、信号、规则、失败和选择；每镜只承担当前最重要的观看任务。

核心原则：镜头不能替场次补作业

如果你还说不清“人物进场时相信什么、离场时知道了什么”，此时设计炫目的运镜只会掩盖结构空缺。先写清变化，再决定怎么拍。

二、把场次写成一台因果机器

这场戏发生在月城记忆控制室，导演母版的连续时间是 29 秒。控制室的空间被安排成一条可读的价值轴：画面左侧是发出金色脉冲的记忆核心，画面右侧是散发冷青光的弟弟救生舱，中央控制台把两者隔开。空间本身已经在讲“全城”与“家人”的对立。

三、先拆九个节拍，再谈八个镜头

节拍是一次最小的叙事变化；镜头是观众观看这次变化的视听容器。二者不是同义词，也不必一一对应。一个镜头可以承载两个紧密相连的节拍，同一个节拍在更复杂的拍摄设计中也可能需要主镜头、反应镜头和插入镜头共同覆盖。

月城案例 为了让表格容易读，本章把本场九拍简写为 B01–B09，把八镜简写为 01–08。进入规范主数据时应使用带命名空间的稳定 ID，例如 B08-01–B08-09 与 SH-081–SH-088；适配 shuohao 时才降成场内位置 1–9。

反应拍在数据里可能“消失”

源码实现 在创作层，B02 与 B05 都应标为反应，因为它们控制观众何时感受人物；但 shuohao 的 script.json 只允许动作或台词两种 beat 结构，所以反应拍必须序列化为 action。内容还在，语义子类型却丢了。

重构建议 在供应商无关的主数据中保留 kind: "reaction"，再由适配器降级成目标格式。

四、把九拍组织成八个镜头

镜头设计需要连续回答三个问题：

  1. 此刻观众最需要知道什么？ 空间、物件、规则、表情或决定只能有一个主次顺序。
  2. 最佳证据在哪里？ 若信息在屏幕上，用插入特写；若变化在人脸上，用反应近景；若冲突存在于空间关系，用全景。
  3. 这一镜为何在这里结束？ 新信息落地、动作改变方向、视线找到对象或声音制造问题，都是合理切点。

七、映射到 Narrative Forge：一个 scene 实际承载一个镜头

源码实现 在 Narrative Forge 24c3c47 的 AI 短剧模式中，static/src/draft.js 的 generateSerialDraft() 通过 POST /api/generate-episode 要求文本模型返回一列 scenes。虽然名字叫 scene，每个元素实际对应这里的一条镜头记录；模型传输格式包含标题、五档景别、时长、动作、对白、转场和首尾状态，并用临时 nextKey 连接下一镜。

不要把模型传输格式误当持久化 schema：安装生成结果后，key/nextKey 会被转换为项目内部的 id/nextSceneId，临时 key 本身不再保存。

十、带走一条可以重写成程序的思维链

现在回看这八镜，真正可复用的不是“大全景后接特写”这个表面套路，而是下面的决策顺序：

  1. 定义变化：阮星从相信能够两全，变成确认必须选择。
  2. 列出证据：活着的弟弟、母亲信号、互斥电路、失败的应急杆。
  3. 排列节拍：先让观众希望两全，再逐步关闭退路。
  4. 分配观看方式：空间用全景，物证用插入，心理冲突用反应特写，行动失败用中景。
  5. 写清状态交接：每镜结束时，下一镜必须接得住人物、道具、视线、光线和未完成动作。
  6. 最后才适配程序：把同一导演母版分别量化为 Narrative Forge 的 scene 列表，或 shuohao 的 script → segment → cut。

一份合格的分镜列表，不只是“要生成哪些画面”。它是一份可追溯的观看计划：每个镜头都知道自己从哪个故事变化而来，交付什么证据，又把什么状态留给下一镜。

一个已经发生的数量语义漂移

源码实现 互动模式的 draftRequestMeta() 已把 nodeCount 定义为 storyNodeCount × shotsPerNode，但 generateStoryDraft() 为“大规模生成”二次确认计算 totalShots 时又乘了一次 interactiveShotsPerNode，提示文案还把这个 nodeCount 称为“剧情节点”。证据定位：static/src/draft.js · draftRequestMeta() 返回值与 generateStoryDraft() 的 totalShots。

重构建议 用不可混淆的 storyNodeCount、shotsPerNode 与 totalShotCount 三字段贯穿估算、请求和安装契约，并为每一层断言 totalShotCount = storyNodeCount × shotsPerNode。

每个 segment 一个目录；export 写 prompt.md 与根部 manifest.json，并记录预期的 f1..fN.png 路径。PNG 必须事先位于目标路径，export 不生成也不复制它们。

七、自包含是有意的重复，不是偶然的重复

源码实现 分镜脚本重新实现剧本的计秒规则，而不是跨目录 import novel-script；它也自己解析配方卡 frontmatter，而不是 import 外部 shot-recipes。源码注释明确给出的理由是：任一 skill 都应能单独拷走。

文档声明 根 README 对组合报告也采用同一原则：组装器调用各 skill 的渲染 CLI，不共享内部模板代码。这样某一 skill 改渲染时，组合报告重新调用即可获得新结果。

收益

  • 安装、复制、测试和故障边界都清楚。
  • 一个 skill 不存在时，其他 skill 仍能运行。
  • 外部卡库不成为分镜的硬依赖。

代价

  • 相同计时、枚举或解析规则会复制，版本漂移要靠测试发现。
  • 跨层契约不是一份正式 schema，而散落在 Markdown、源码和夹具里。
  • “可单独拷走”弱化了端到端迁移与版本兼容的显式管理。

分析推论 这是一个明确的架构取舍，不应简单重构成共享工具包。若未来改成平台型应用，可以抽出版本化领域契约；若仍以可搬运 skill 为产品形态，重复实现反而是部署隔离的一部分。

一、先确定现行模型：以 segment → cut 为准

文档声明 根 README、storyboard schema 和 SKILL 后半部描述的是三层结构：集（episode）→ 生成段（segment）→ 分镜切（cut）。段对应一次计划中的视频生成调用，cut 是段内的剪切，关键帧按 cut 准备。

源码实现 validateStoryboard() 要求每集有 segments，每段有 sceneIndex、cuts 和 h3Prompt；gateReport() 对段总时长、cut 时长和段内 H3 切点分别检查。源码没有现行的顶层 shots 数组。

测试约束 selftest 明确断言样例为 10 个 segment、34 个 cut、17 道门；seed 结果被断言为 segments.length === 0，而非 shots。

同一份 SKILL 里保留着上一版词汇

文档声明 SKILL 开头一张旧表还写“单镜头 ≤15 秒”“首帧 + 运动双提示词”和“每镜一段 H3”，Step 1 也写“shots 留空”。这些说法与同文件后文、schema、样例及源码不一致。

分析推论 学习当前实现时，应把它们视为文档漂移，而不是同时存在的另一套合法格式。现行合同是：segment 受 maxSegmentSeconds 约束（默认 15 秒），cut 受 minCutSeconds..maxCutSeconds 约束（默认 2–5 秒），每 cut 一个 frame，每 segment 一个 h3Prompt；顶层 params 可以覆盖这些时长默认值。

六、h3Prompt：把多张关键帧钉到段内时间线上

源码实现 对每个 segment，cutStarts() 从 0 开始累计前面 cut 的秒数。例如 3、4、3 秒三切的起点是 0、3、7。h3CutTime() 把起点格式化成 00:03.000；h3AlignmentLine() 再把 Picture 1..N 与这些时刻组成必须逐字匹配的首行。

1

图片对齐首行

单切使用固定 I2VA 句式；多切逐张写 Picture k 对齐第几秒。

2

视听描述

文档声明 [Shot 1] 起；文档要求第 2 切以后用自己的累计切点开行。源码实现 当前门只确认对应 marker 在 H3 正文中出现，没有证明它位于行首；每切运镜词则会在自己的 Shot 切片里检查。

3

整体音景

overall_soundscape 写环境、动作与非语言人声；画面动作改变时也要同步。

4

非叙事配乐

non_diegetic_music 写观众听见、角色听不见的配器与速度；无则 N/A。

源码实现 每个被 cut 认领的台词必须逐字出现在 <d>[标签] …</d> 块中；正则接受任意非空方括号标签，并不限定必须是 [Chinese]。语言检查先从 H3 中剔除 <d> 块和同一行双引号内容：promptLang === "en" 时，剩余正文出现 CJK 才失败；任何非 en 值都走中文 token 回退，只要求剩余正文至少有一个 CJK，不阻止中英混写，也不校验枚举。每个 frame 无论 H3 语言如何都必须非空且不含 CJK。

文档声明 说话人的身份、音色、语气写在 <d> 外；VO 另写画外音与闭唇指令。声景不是纯后期备注：文档把它视为可能驱动画面动作的生成指令。

两个时间轴：全片时间与段内时间

源码实现 每个 segment 都是独立生成单元，因此它自己的 Picture 1 永远钉在 0.00 秒，后续 cut 起点也只在本段内累计。跨三个段的 29 秒场次，H3 会拥有三条各自从零开始的局部时间线，而不是一条连续的 0–29 秒提示。

分析推论 后续剪辑或编排器必须另行保存“段在整集中的全局起点”。当前 manifest 记录段内 cutStarts 和段时长，却没有给段写全局 timecode。

证据入口：novel-storyboard.mjs::cutStarts()、h3CutTime()、h3AlignmentLine()、h3CutSlices() 与 gateReport() 的 H3 分支；references/h3-prompt.md。

2 · segment-cap每段 cut 秒数总和大于 0 且不超过 maxSegmentSeconds。storyboard params/cuts不能证明目标视频模型真的支持该时长。
3 · cut-length每切落在 minCutSeconds..maxCutSeconds。cut seconds不能证明节奏适合此处情绪。
4 · dialogue-fit被认领台词的估算秒数之和不大于 cut 秒数。script flow + 语速参数不能证明演员实际能自然说完。
5 · ep-duration整集所有段总时长在 script 目标的容差内。script targetSeconds不能用单场切片冒充整集通过。
6 · crowd画内人物不超阈值；超出时 cut 或 segment 必须有 note。cut characters/notenote 的拆解是否真正可生成仍要人看。
7 · segment-id段号精确等于 E{集号}-{顺序号}，集内连号。episode/curr index不提供跨版本稳定身份。
8 · size-phrasesize 在五档枚举内，且对应英文短语出现在 frame。cut size/frame不能检查生成图片实际景别。
9 · camera-phrasecamera 属于词表，且出现在自己的 H3 Shot 段落。cut camera/h3Prompt不能证明运镜合理或可实现。
10 · h3-structure首行由 cuts 推导后逐字一致；三个核心字段齐全有序；第 2 切起的时刻正确。cuts/h3Prompt/promptLang不能证明自然语言描述有美感。
11 · h3-dialogue认领的每句台词逐字进入 <d> 块。script flow/h3Prompt不能证明声线、口型或表演正确。
12 · h3-langen 拒绝剔除台词块与双引号内容后仍含 CJK 的正文；其他值使用中文 token，并只要求剩余正文至少含一个 CJK。promptLang/h3Prompt不校验 promptLang 枚举、不阻止中英混写，也不是完整语言识别。
13 · style-phrasestyle 在预设内，每条 frame 含同一预设英文短语。style/frame字符串一致不等于画面真的统一。
14 · prompt-english每条 frame 非空且不含 CJK。frame不验证英文语法或提示质量。
15 · prompt-no-namesframe 禁 outline/cast 人名；英文 H3 正文也禁人名。无 outline/cast 时显式跳过姓名库部分。可选 outline/cast无法识别没列入上游的别称。
16 · refs集与 sceneIndex 存在；cut 人物、道具是 script 该场集合子集。script不直接对账 art，因为合法集合已经由 script 承接。
17 · shot-recipe挂卡库时：配方 ID 存在、必备短语进入 frame、多格配方连续使用达到下限。可选 --shots 目录建议景别/运镜只提示偏离，不设硬门。

测试约束 selftest 直接断言 gateReport(...).length === 17，并为覆盖遗漏/重复、错误时长、H3 切点、语言、配方缺失等分支构造失败夹具；它还断言不给上游时相应门以带“跳过”说明的通过状态返回。

源码实现 validate/checkup 默认把每次运行和失败门追加到当前目录的 .gates.jsonl；stats 统计最常失败和从未失败的门。加 --no-log 可停记，写日志失败会被静默吞掉，不阻塞校验。

八、第 17 门为何是可选的：公开仓库没有完整卡库

源码实现 loadRecipes() 只读取指定目录顶层的 .md，以受限 frontmatter 解析 id/name/cuts/must_phrases/sizes/cameras 等机器字段。CLI 拒绝导出的 JSON，也会在目录不存在或没有卡片时直接报错，避免“用户以为挂上了，实际没生效”。

源码实现 挂库后，每个 cut 可有一个 recipe。must_phrases 以双方小写后的 includes 检查；卡片最小 cuts ≥2 时，同一 segment 内同 ID 必须连续出现足够多切。sizes 和 cameras 只由 recipeDrift() 产生报告提示，不使门失败。

文档声明 仓库内的迁移设计把完整 shot-recipes 迁往一个名为 shuohao-video-skills 的私有仓库作为目标；公开侧的合并提交与当前目录证明卡库已被清理，并以三张最小 fixture 保持分镜自测自包含。私有侧是否收到完整且当前的卡库不在本次审计范围。

测试约束 selftest 读取的正是 references/test-fixtures/shot-recipes 三张测试卡，覆盖未知 ID、缺必备短语、多格不够和建议偏离不设门；这些夹具证明接口行为，不代表完整私有镜头语汇库的内容。

资料缺口必须保持为资料缺口

分析推论 仅凭公开接口可以评估“卡如何被消费”，不能评估完整卡库的镜头分类、覆盖面、审美质量或授权状态。没有私有仓库访问权时，不应从卡名和三张测试夹具反推出全库。

最重要的判断

分析推论 shuohao storyboard 是一份很强的单一路径 AI 视频生成规格：它对节拍覆盖、时长、提示词和参考图订单的纪律，远强于只写“镜号 + 画面”的松散表格。但它不是完整的影视分镜领域模型，也不是视频生产系统。

重构建议 最合理的继承方式不是推翻它，而是把它放在统一主数据之后：稳定场次/节拍/镜头关系负责长期编辑，shuohao adapter 负责把一条批准路径压成 segment、cut、H3 和 manifest。

第七章 · Comparative Systems

不是谁赢，而是谁保留了哪一种决定

Narrative Forge 把创作、预览、媒体生成和导出收进一个浏览器工作台；shuohao-skills 把小说改编拆成五份可校验、可交接的 JSON。两者解决的问题重叠，却不在同一抽象层。真正有用的比较，不是数功能按钮，而是沿同一条生产链追问：哪项决定被结构化保存，哪项只活在提示词里，哪项在适配时不可逆地丢失。

先把比较对象放在同一张坐标纸上

源码实现 Narrative Forge 本地固定提交 24c3c47 的核心对象是一个可编辑项目：互动模式保存带 choices 的镜头图，短剧模式保存 episodes[].scenes[] 的线性镜头；同一项目还能直接发起图像、视频和导出任务。核对入口是 static/src/project-model.js、static/src/draft.js、static/src/api.js、app.py 与 backend/route_registry.py。

源码实现 shuohao-skills 固定提交 4322897 的五个确定性脚本分别消费和产出 outline.json、cast.json、art.json、script.json、storyboard.json；脚本负责 seed、validate、render 和 export。文档声明 语义创作由读过 SKILL.md 与 pass 文档的 agent 完成。核对入口是根 README.md、各 skill 的 SKILL.md、references/schema.md 与 scripts/*.mjs。

校验 测试约束 前后端测试覆盖启动、项目读写、供应商秘密、媒体参数、导出与部分草稿安装；生成结果安装器还限制重复 key、目标引用与规模。见 static/src/*.test.js、backend/test_server.py。 测试约束 五个 selftest.mjs 用击穿夹具保护各层确定性逻辑；storyboard 进一步检查 exact-once beat 覆盖、时长链、引用和 H3 对账，第 17 道 shot-recipe 门仅在挂载卡库时启用。 分析推论 shuohao 的跨层确定性门更强；Narrative Forge 的真实媒体与导出路径更完整。两者的测试都不能证明镜头节奏、表演或构图已经好看。

最终输出 源码实现 可保存项目 JSON 与素材，并通过后台 job 生成互动试玩包或短剧分集成片包；互动和短剧导出是两条不同端点。见 export_player()、export_serial()。 源码实现 五阶段输出 JSON、Markdown、单页报告；storyboard 另导出 H3 提示文件、切点 manifest 与关键帧槽位，不合成最终视频。 分析推论 前者交出可播放候选，后者交出可复核制作包。选择哪一个取决于你需要“立即运行”还是“逐层审计”，并非输出文件越多越成熟。

强项来自边界，弱项也来自同一个边界

Narrative Forge：短反馈回路

分析推论 它最有价值的不是某条提示词，而是从镜头编辑、参考图、生成任务到播放器／导出的短回路。需要快速验证互动路线或逐镜媒体结果时，集中式项目状态减少了文件搬运。

分析推论 代价：故事节点、场次、节拍、镜头和任务挤在少数对象里；越往大型项目、多人协作和重新生成发展，越难判断一次修改影响了什么。

shuohao：显式交接与质量门

分析推论 它最有价值的是每一阶段都能单独 seed、审阅、validate 和 render。长篇小说改编、批量分集和稳定资产 ID 需要大量对账时，这种文件契约比一份不断膨胀的项目对象更容易诊断。

分析推论 代价：流程面向线性短剧并深度绑定位置索引与 H3 投产格式；没有持久任务、分支状态或成片执行层，跨阶段修改仍依赖操作者重跑正确命令。

共同缺口：来源、批准与派生没有闭环

分析推论 两者都能保存“现在是什么”，却不能系统回答“谁在何时批准了哪个来源版本”“哪些字段是人工决定”“哪些提示和媒体因上游修改而失效”。这不是多加一个时间戳可以解决的问题。

私有能力不能用想象补齐

文档声明 shuohao 的 docs/superpowers/specs/2026-08-21-shot-recipes-repository-migration-design.md 称完整 shot-recipes 卡库已移至私有仓库；公开提交只有挂载接口、迁移说明与最小测试夹具。

分析推论 因而不能把未审计卡库算作公开系统的完整镜头知识，也不能据此贬低或拔高现有质量门。

信息损失账本：先看不可逆，再看是否方便

什么时候选哪一种，什么时候不该二选一

快速做出可玩的互动原型

分析推论 优先利用 Narrative Forge 的剧情边、播放器、媒体任务和试玩导出；同时把复杂条件与汇流状态另存，不要假设满树生成器就是最终叙事模型。

从长篇材料批量改编线性短剧

分析推论 优先利用 shuohao 的阶段 JSON、稳定 C/S/P 资产 ID、时长对账和质量门；同时尽早替换场次与 beat 的位置索引，避免中途插入导致全链漂移。

要长期维护自己的生产系统

分析推论 不要简单把一个仓库塞进另一个。保留 Narrative Forge 的短执行回路与 shuohao 的显式契约，把两者接到供应商无关的规范领域模型上。

只需一次性教学或概念验证

分析推论 选择更短的路径即可。规范模型的价值来自变化、重跑和协作；若没有这些成本，过早建设完整平台反而会淹没创作问题。

本章结论

分析推论 Narrative Forge 的优势是执行闭环，shuohao 的优势是交接契约。前者容易把叙事层压进镜头与项目状态，后者容易把通用导演意图压进线性位置索引与特定视频协议。重构建议 重建时不应复制两边所有字段，而应先保存那些一旦丢失就无法可靠重算的创作决定，再把按钮、报告、提示与任务当成可替换的消费端。

第八章 · Canonical Domain Model

先保存创作决定，再编译供应商格式

重构建议 这一章提出一套供应商无关的规范模型。它不是 Narrative Forge 或 shuohao-skills 已经实现的 schema，而是一张可供重写、迁移和长期演进的设计底图：故事事实、导演决定、生产任务和具体文件各有自己的身份。系统默认编译的提示词是可重建的 derived Artifact；人工改写后，它就成为有来源记录的 authored override。

六条不变量，比字段数量更重要

重构建议 先把系统必须长期守住的关系写成不变量，再决定用 TypeScript、Python、SQLite 或别的技术实现。否则，即使对象名看起来专业，同一项决定仍会在提示词、页面状态和导出文件之间产生三份互不相认的真相。

  1. 身份稳定：业务实体获得不可变 ID；标题、顺序和文件名变化时，引用不随之改变。
  2. 层级不混：故事图、集、戏剧场次、节拍、镜头、画格、生成段和执行任务分别建模。
  3. 决定可溯：人工撰写、人工覆盖、规则派生和模型生成都记录来源及输入版本。
  4. 关系可多对多：一个 beat 可以被主镜、反应镜和插入镜共同覆盖；一个 shot 也可以承担多个 beats。
  5. 分支可汇流：选择边不仅指向节点，还描述条件、状态补丁和 join 前必须满足的兼容规则。
  6. 批准绑定版本：“已批准”指向精确 revision；上游改变后，受影响的派生产物会过期，而不是继续冒充最新版。

分析推论 更细的模型会增加录入和迁移成本；它的收益只在修改、重跑、审阅、协作或更换供应商时兑现。因此应让简单项目使用合理默认值，而不能为了表面简洁再次合并概念。

重构建议 ShotBeatLink 应是有 ID 的关系记录，而非藏在两边的 ID 数组；它至少保存 role、coverageWeight 和 order。这样主镜、反应镜、插入镜以及一个长镜覆盖多个 beats 都能被显式表达。

草稿、快照与迁移隔离区不是同一层

重构建议 作者编辑时，关系指向稳定 ID，写入通过 expectedRevision 防冲突；到编译、执行或发布边界，系统才把全部可达 ID 解析为 CanonicalSnapshot 里的精确 revisions。这既避免草稿关系过度繁琐，也防止一次任务在途中消费新修改。

重构建议 无法无损对应 DramaticScene、Beat 或 StoryGraph 节点的旧记录进入 MigrationRecord，而不是放宽规范模型的“无孤儿”不变量。隔离记录可审阅、可重跑，但不得被批准、生成或发布；晋升动作必须创建完整规范关系并写入 provenance。

分支汇流、版本和人工批准必须说清“哪一个”

分支不是树形文件夹

重构建议 每条 edge 保存版本化的声明式条件与 statePatch；条件由白名单谓词解释，绝不把字符串交给 eval。join 节点声明必须相等、允许并集或需要人工选择的状态字段，验证器对所有入边求兼容性。

版本不是一个全局数字

重构建议 每个实体维护 append-only revision、baseRevision 与内容哈希；项目的 schemaVersion 只说明格式，不说明某一镜头是否最新。

批准不是布尔值

重构建议 Approval 保存对象 ID、revision、批准范围、批准人和时间。上游 revision 改变后，影响分析把相关批准标为 superseded 或 needs-review。

重构建议 写 API 时要求客户端提交 expectedRevision；不一致就返回冲突和最小 diff。生成任务只接受已批准 revision 的不可变快照，因此一次失败重试不会意外消费用户刚改到一半的页面状态。

本章结论

重构建议 规范模型的核心不是多建几张表，而是把不可逆的创作决定从供应商格式中解放出来。稳定 ID 保护身份，多对多 link 保护覆盖意图，revision 与 Approval 保护人工决定，Provenance 保护可解释性，ProviderAdapter 则让提示词、请求和文件布局保持可替换。

第九章 · Rebuild Roadmap

先立规范层，再替换执行层

重构建议 不必先决定“把哪个仓库重写掉”。更稳妥的顺序是：冻结真实样本，建立供应商无关的规范层，做两条只读导入，再让旧工作台与新执行器同时消费它。每一个里程碑都必须交付可回滚的用户价值，而不是等一个宏大平台全部完成才第一次运行。

当前 fork 的实施决定（2026-08-30）： 后续讨论选择了“同仓并行开发、最终独立成仓”的混合路线；该迁移现已完成，独立产品命名为 Plotloom · 叙织。Plotloom 只创建新项目，不导入或双写 v1 数据，其后端、前端、提示词、迁移和测试禁止依赖 v1 运行时代码。本章后文关于旧项目导入与规范 sidecar 的内容保留为方案比较和被拒绝路线，不是当前实现承诺。权威工程合同见 docs/adr/0010-plotloom-clean-repository.md 与 docs/provenance/initial-extraction.md。

先判断问题属于实现，还是属于合同

源码实现 Narrative Forge 本地固定提交 24c3c47 已实现浏览器编辑、项目保存、图像／视频任务和两类导出的完整代码路径；主要入口是 static/src/main.js、project-model.js、api.js、app.py 与 backend/route_registry.py。分析推论 这些交互面是渐进改造应优先保护的现有产品能力；它们在某一具体部署中是否可用，仍需另做运行验证。

源码实现 shuohao-skills 固定提交 4322897 已把 outline、cast／art、script、storyboard 拆成可 seed、validate、render、export 的文件合同；其确定性 Node 脚本不负责调用模型完成语义创作。分析推论 它适合成为导入、验证和编译参考，而不是直接充当在线任务服务。

分析推论 两边真正共同的根因不是“少一个按钮”：故事、导演覆盖、供应商提示、任务状态和文件来源之间缺少稳定的规范合同。只修页面或把五阶段脚本包进 HTTP，不会自动得到可追溯、可分支、可换供应商的系统。

重构建议 表 1　依据风险选择改造方式，而不是依据个人技术偏好

数据迁移项目量大、字段含义不一致、必须逐步核对。只有少量测试项目，并能人工确认全部迁移结果。迁移 dry-run、差异报告与回滚演练。

协作与版本仍是单用户、本地优先，可晚些增加冲突模型。多人并发、审核与权限是首个版本的硬需求。角色矩阵、并发场景和审计要求。
供应商更换先把现有三类请求移到 adapter，保持 UI 不动。现有协议散落到每个业务对象，抽离成本超过重做执行层。调用图、能力矩阵与黄金请求夹具。

重构建议 默认路线采用“绞杀者”式渐进改造：旧系统继续服务用户，新规范层先做只读镜像，再成为写入真相，最后逐个替换提示编译、任务、导出和 UI。只有当迁移样本证明旧边界无法被隔离，才把某一模块独立重建；不要一次性重写整个产品。

分析推论 渐进路线会暂时增加“双模型”复杂度；整体重建则把所有风险推迟到最终切换日。前者需要明确的单向同步和淘汰日期，后者需要真实等价性证据。两者都不是免费的捷径。

非目标：先保护范围，才有可能验收

重构建议 第一轮重建明确不承担下列目标；需求若改变，应单独写 ADR、威胁模型与验收计划，而不是顺手塞进里程碑。

  • 不自动判定“镜头是否好看”；机器只检查可证明的合同，艺术判断由人批准。
  • 不复制、猜测或重新分发 shuohao 未公开的完整 shot-recipes 私有卡库。
  • 不复刻任一供应商的全部 API；只实现当前项目确实需要且可测的能力子集。
  • 不在首轮建设模型训练、素材市场、实时协同编辑或完整云端账号系统。
  • 不把旧项目原文件就地改写；导入始终产生新规范项目和可审阅报告。
  • 不保证不同生成模型像素级一致；保证的是输入快照、能力映射和结果来源可解释。

目标模块：领域核心不认识浏览器，也不认识模型品牌

Core Domain

重构建议 实体、值对象、revision、StoryGraph、coverage、continuity 和 approval 规则；禁止网络、环境变量和具体文件路径进入。

Application Services

重构建议 负责“批准镜头”“编译生成段”“重试任务”等用例和事务；只通过端口访问存储、队列和适配器。

Boundary Adapters

重构建议 HTTP、CLI、旧项目导入、shuohao 导入、供应商协议和导出布局各自独立，降级规则可测试、可替换。

API、存储与任务：从第一天就允许重试和恢复

重构建议 表 2　首个可用版本的基础设施合同
边界建议合同必须避免
资源 APIGET /projects/:id、PATCH /shots/:id、POST /approvals；写入携 expectedRevision，冲突返回当前 revision 与差异。发送整份项目并静默覆盖并发修改。
命令 APIPOST /generation-segments/:id/tasks 接受已批准 snapshot ref 与幂等键，立即返回 task ID；查询、取消和重试是独立端点，取消结果明示 confirmed、pending 或 unsupported。让长模型请求占住页面 HTTP 连接，或重试时重复扣费。
元数据存储本地优先先用 SQLite 外键、事务和 WAL；Repository 接口允许未来切到 Postgres。把每个实体散落成无法原子提交的多份可变 JSON。
产物存储文件按内容哈希寻址，数据库保存 MIME、尺寸、来源和逻辑引用；接口允许未来接对象存储。用供应商临时 URL 或用户标题充当永久文件身份。
任务状态queued → cancelled | running；running → succeeded | failed | cancel_requested；供应商确认后才进入 cancelled，竞态中仍可 succeeded／failed。attempt 保存 lease、时间、错误类别和外部 job ID。把“页面不再轮询”当成供应商任务已取消，或只在内存 Map 保存唯一事实。
事件与失效事务内写 outbox；worker 领取后编译，输入 revision 改变则把下游 Artifact 标 stale。依赖前端“记得按正确顺序重跑”。

重构建议 API 返回领域错误码，例如 REVISION_CONFLICT、GRAPH_JOIN_INCOMPATIBLE、ADAPTER_CAPABILITY_MISSING 和 ARTIFACT_INPUT_STALE，同时提供实体 ID 与修复上下文；不要只返回模型供应商的原始字符串。

重构建议 取消 queued 任务可在提交前当场确认；已提交的任务只有在 adapter 声明 supportsCancel 且供应商确认时才可标记 cancelled。若能力不支持，命令返回 unsupported，任务继续并由后台对账；页面可停止观察，但这只是 UI 状态，不改写任务事实。

分析推论 SQLite 加本地文件系统能以最低运维成本提供事务和可恢复任务；它不适合多机并发 worker。真正出现跨机器吞吐需求时，再以已存在的 Repository、Queue 和 ArtifactStore 端口替换为 Postgres、消息队列和对象存储。

导入 Narrative Forge：保留原义，不替旧字段美化身份

源码实现 截至 24c3c47，static/src/project-model.js 的 normalizeProject() 把项目结构归一为版本 6；短剧以 episodes[].scenes[] 保存线性镜头，互动以 storyNodeKey 把一个剧情节点下 1–5 个 shots 分组，组尾承担后继／选择。分析推论 UI 中的 project.scenes 是当前模式或当前集的操作门面，不应被当成另一份规范数据导入。

重构建议 导入器按下列次序运行，并始终输出 dry-run 报告：

  1. 封存来源：复制原始 project JSON 为只读 Artifact，记录 SHA-256、来源提交、导入器版本和时间。
  2. 映射项目与资产：meta → Project；characters、sceneCards → Asset。保留旧 ID，另存 legacyRef。
  3. 暂存短剧：Episode 可直接建立；每个旧 scene 作为“候选 Shot 规格”进入 MigrationRecord，因为 serial 合同中它近似镜头，但尚没有可归属的 DramaticScene 与 Beat。
  4. 暂存互动：相同 storyNodeKey 的 1–5 个旧 scene、组内顺序、组尾选择／next 和原目标全部进入 MigrationRecord；在语义节点尚未建立时，它们不冒充规范 StoryGraph。
  5. 晋升规范实体：只有明确规则或人工确认后，才从暂存记录同步创建 DramaticScene、Beat、Shot、ShotBeatLink 与 StoryGraph 节点／边，并记录晋升 provenance；基于 action 文本的候选带 confidence，不冒充原始事实。
  6. 保存派生历史：旧 imagePrompt、videoPrompt、媒体 URL、prediction ID 和本地路径作为 legacy Artifact／Provenance 导入，不提升为规范创作字段。

迁移硬边界

源码实现 serial 的 scene ≈ shot；interactive 则是 1–5 个 shots 组成一个 storyNodeKey 节点。

重构建议 导入器必须按 mode 分派，绝不能用一条“scene → DramaticScene”映射处理两者。未晋升的 MigrationRecord 不能被批准、编译、生成或发布；这是迁移隔离区，不是放宽规范模型“无孤儿”验证的理由。

导入 shuohao：先把位置引用变成稳定身份

源码实现 截至 4322897，C/S/P 是 cast／art 层的稳定资产 ID；script.json 每条场次记录的 sceneId 引用地点／场景美术资产，而 storyboard 的 sceneIndex 指剧本中的场次出现位置，beats: [start, end] 也使用位置区间。依据是 skills/novel-script/references/schema.md、skills/novel-storyboard/references/schema.md 及相应 scripts/*.mjs。

重构建议 导入顺序必须从上游文件逐层建立 ID 映射，不能从 storyboard 倒猜：

  1. 封存五层输入：每份 JSON 保存原文件哈希、skill 版本、路径和导入器版本；原始数组顺序永远可回查。
  2. 资产映射：C/S/P 转为 Asset，并保存 legacyRef；ID 冲突按来源命名空间处理，不重编号原文件。
  3. 场次身份：为每一集中的剧本场次出现创建稳定 DramaticScene ID；旧 sceneId 仅写入该场次的 locationAssetId，不能与新场次 ID 交换。
  4. 节拍身份：按 scene occurrence + 原位置为 flow 条目分配 Beat ID；文本、类型、说话者和原 index 一并保存。
  5. 覆盖映射：storyboard sceneIndex 先解析到稳定 DramaticScene；cut 转为 Shot，beats 区间展开为 ShotBeatLink，并保留原范围供往返核对。
  6. 生产映射：segment 转 GenerationSegment；英文 frame 与 h3Prompt 作为带输入哈希的派生 Artifact；若有实际关键帧文件，另建文件 Artifact。
  7. 门结果映射：.gates.jsonl 和报告作为验证 Artifact 导入；可选 shot-recipe 未运行或卡库缺失必须记为 skipped，而不是 pass。

迁移硬边界

源码实现 sceneIndex 是剧本场次位置，sceneId 是该场引用的地点／场景资产标识。

重构建议 把二者交换会制造表面引用合法、语义完全错误的数据，必须用迁移夹具专门击穿。

艺术与产品 eval

重构建议 用固定场景由人工盲评叙事清楚度、空间连续、表演可读、节奏和修改成本；记录 rubric、评审者与输入 revision，不把主观分数伪装成单元测试。

分析推论 两套旧系统的校验优势应被保留，但不能原样合并成一张更长的 gates 清单。每道门必须归属某一合同、给出可行动错误，并证明一次真实失败；否则它只是仪式性复杂度。

隐私与安全：创作工具也处理秘密和不可信输入

源码实现 Narrative Forge 24c3c47 的 README.md 明确说明本地服务没有账号和访问控制，远程部署必须保持私有；app.py 的 validate_media_url() 拒绝本机／内网媒体地址，供应商配置端点不返回密钥。分析推论 现有防线应作为迁移回归基线，而非新架构已经安全的证明。

  • 重构建议 长期密钥来自进程环境或专用 secret store；浏览器覆盖仅限 session，数据库只保存 secretRef。
  • 重构建议 默认只监听 loopback；远程入口必须有认证、TLS、授权和审计，否则保持私有网络。
  • 重构建议 所有外部 URL 防 SSRF 与 DNS rebinding；下载限制协议、重定向、IP 范围、大小、超时和 MIME。
  • 重构建议 文件路径由服务器生成，禁止用户输入参与目录拼接；Artifact 落盘后计算哈希并做类型探测。
  • 重构建议 小说、提示和第三方仓库文本一律作为数据；不得把其中指令提升为系统命令、工具授权或模板代码。
  • 重构建议 日志默认脱敏并设保留期；按项目限制并发、文件大小、预算和重试次数，昂贵操作要求明确批准。

分析推论 如果产品继续是单用户私有工具，完整多租户权限系统可以不是首轮目标；一旦公开联网或多人共享，它就从“未来增强”变成上线前置条件，不能靠免责声明代替。

最终验收：能解释一次修改怎样走到一个文件

重构建议 只有以下清单在同一个候选版本上全部成立，才可以称根本合同已被修复，而不只是新页面可以点击。

  • 作者编辑关系使用稳定 ID，移动顺序不改变身份；编译、执行与发布只消费已批准 CanonicalSnapshot 中的精确 revisions。
  • NF serial 与 interactive 多镜节点、shuohao sceneIndex 与 sceneId 均按各自语义无损导入；暂存记录要么晋升为完整规范关系，要么被明示阻止执行与发布。
  • 一个 beat 可被多个 shots 覆盖，一个 shot 可覆盖多个 beats；验证器能定位缺口与有意重叠。
  • 分支入口可达、终点合法、join 状态兼容；条件和状态补丁可被回放。
  • 人工批准绑定精确 revision；上游变化会标记受影响 Artifact stale，而不覆盖人工 override。
  • 同一 adapter 版本和输入快照编译出相同请求；不支持能力产生显式降级决定。
  • 任务在每个故障边界重启后保持幂等与可追踪；只在提交前或供应商确认后进入 cancelled，不支持取消时继续后台对账，不重复收费或遗失结果。
  • API、日志、项目、导出和 Artifact 均扫描不到真实密钥；远程部署边界有可验证控制。
  • 从任一生成视频可反查任务、adapter、提示 Artifact、输入 revisions、人工批准和来源文件哈希。
  • 旧系统清退前完成备份恢复与回滚演练，操作者能按 runbook 在限定时间恢复服务。

本章结论

重构建议 先用冻结夹具证明旧数据是什么意思，再用规范核心保护这些意思；先做只读导入，再建立事务与任务；先让 adapter 替换供应商耦合，再切换唯一写入源。这样可以同时保留 Narrative Forge 的短反馈回路与 shuohao 的显式交接，而不继承它们最难演进的对象混用和位置引用。

重构建议 路线中的目标架构、API、存储、任务、安全和里程碑均为提案。现状依据固定为 Narrative Forge 24c3c47 与 shuohao-skills 4322897；具体证据路径在本章相邻段落、第七章和 SOURCES.md 中列出。私有 shot-recipes 卡库不在迁移或验收承诺内。

读代码、改流程、验收分镜

这一章不是让你真的拿纸笔完成整套制作，而是把前面的知识压成一套可重复查询的方法：拿到任何故事生成项目时，知道先问什么、沿哪里追代码、哪些产物应该存在，以及什么情况下可以修改、应该重构或值得重写。

一、理解第三方系统的四遍阅读法

不要从文件树第一行一直读到最后一行。每一遍只追一种问题，读完都应留下一个可以验证的产物。

第一遍：用户动作

从一个真实按钮或命令开始，追到它产生的最终文件、页面或媒体任务。

  • 入口是什么？
  • 中途跨过哪些模块或进程？
  • 失败会在哪里暴露？

留下：一张端到端调用图。

第二遍：数据生命史

选择一个概念，例如“场次”或“镜头”，追踪它从输入、内存、持久化到导出的每次变形。

  • 何处获得 ID？
  • 哪些字段是创作者输入？
  • 哪些字段会被重新计算或静默丢弃？

留下：一张字段转换表。

第三遍：失败契约

读校验器、测试和回退逻辑，而不是只读成功路径。

  • 什么输入会被拒绝？
  • 什么错误会被默认值掩盖？
  • 测试保护的是格式、行为还是创作质量？

留下：一张失败模式清单。

第四遍：可替换边界

假设更换文本模型、视频模型、存储或前端，观察哪些数据仍然成立。

  • 核心事实是否混在提示词里？
  • 供应商参数能否由通用规格派生？
  • 人工修订能否跨重新生成保留？

留下：一张重构接缝图。

每次都用同一个小案例

用“月城控制室”这样的短场景做探针，比直接输入一部长篇更容易看清信息在何处丢失。探针应同时包含空间、道具、反应、短对白、连续状态和一个形式差异；这样一轮运行就能触碰多数关键契约。

GenerationSegment为一次计划中的视频生成组织的连续时间单元，可包含一个或多个镜头。戏剧场次或最终剪辑片段。
GenerationTask一次可执行、可重试、有输入快照和供应商参数的工作。通用镜头规格。
Artifact一次执行产生的图片、视频、音频、字幕、报告或清单。任务本身或抽象资产引用。
ContinuityState某个边界时刻人物、道具、空间、光线、声音和知识的可检查状态。“气氛紧张”这样的形容词。
Prompt默认是由已批准事实、导演选择、参考资产和供应商协议编译出的 derived Artifact；人工编辑后，晋升为带 provenance 的 authored override／approved prompt Artifact。系统唯一真相，或可被重编译静默覆盖的匿名文本。
ProviderAdapter把通用规格转换成具体模型协议、枚举、时长和文件布局的边界模块。隐藏在业务对象里的供应商条件分支。
Provenance说明一个结果来自哪些来源、版本、人工覆盖和生成执行的记录。只有创建时间的日志。
Gate可机械判定、失败时能指出具体对象和修复方向的契约检查。“感觉不够电影感”的主观评分。

五、先判断问题在哪一层，再决定怎么改

第三方项目最容易出现的维护错误，是在最靠近症状的地方加条件。先判断失败的是故事、领域契约、适配器还是界面，才能把修复放到真正拥有该规则的层。

只改配置

适用：模型地址、时长上限、提示语言或安全部署参数发生变化，但通用故事与镜头契约没变。

警报：为了新供应商去改故事字段或镜头语义，说明适配边界不存在。

改适配器

适用：通用的 5 秒镜头需要映射到供应商六档时长，或同一关键帧需要不同上传协议。

警报：适配器开始决定人物做什么、哪条分支成立，说明它越权进入创作层。

改领域模型

适用：无法表达一个节拍被多个镜头覆盖、同一地点出现于多场戏、分支汇流或人工覆盖来源。

警报：只往自由文本里补标签，会延迟而不是解决结构缺口。

改工作流

适用：系统在场次未批准前就生成昂贵视频，或每次改台词都必须重做不相关资产。

警报：增加更多按钮，却没有定义批准点、失效传播和恢复路径。

渐进重构

分析推论 适用：经真实使用证据确认，现有界面、媒体任务和导出仍有价值；可以在旁边建立规范模型与双向格式转换器。

前提：能写出兼容测试，并允许一段时间内新旧表示并存；但任一功能在任一时刻只能有一个写入权威，另一侧只做只读投影与差异观察。

完全重写

适用：核心对象无法表达目标产品、状态变化难以迁移，且保留旧架构的成本高于重建。

前提：先冻结行为样本、数据迁移和验收标准；“代码不好看”本身不构成重写理由。

六、怎样判断自己已经真正理解

“我能读懂代码”还不够。达到下面四级，才从会使用走到有能力重建。

  1. 能解释 不用仓库术语，向另一个人解释粗梗概如何变成场、节拍、镜头、画格和生成任务，并说明每层为什么存在。
  2. 能追踪 任选一个镜头，从 UI 或 JSON 追到提示、请求、任务、文件和回读状态；能指出中间每次字段改名与信息损失。
  3. 能预测 在运行前预测：删掉一个 beat、改变一个供应商时长或插入一个互动汇流节点，会使哪些产物失效、哪些不应重算。
  4. 能替换 把文本模型、媒体供应商或存储实现换掉，而不改故事事实和导演母版；适配结果可以重新生成，人工批准不会消失。

一个很实用的闭卷测试

关掉仓库，只看《月城失物局》中“月城控制室”这场戏的粗梗概。尝试口头重建：SC-03 与 SC-08 为什么是两场戏；九拍为什么变成八镜；镜 08 的线性与互动版本究竟在哪一层分叉；29 秒进入两套系统后为什么会变形。能把这些因果讲清，再回到代码验证，你学到的才不是文件路径记忆。

七、以后拿到任何生成式影视仓库，先问这十二题

  1. 系统把来源故事和模型补写的内容分开保存了吗？
  2. 故事节点、戏剧场次、地点资产和镜头是独立对象吗？
  3. 节拍到镜头是一对一，还是能表达多对多覆盖？
  4. 线性后继、互动选择和分支汇流由哪一层拥有？
  5. 每个镜头的入口／出口状态能否机械检查？
  6. 时长是导演决定、估算、供应商枚举还是媒体实测？
  7. 提示词能否从规范数据和资产引用重新编译？
  8. 人工修改会不会被下一次生成静默覆盖？
  9. 模型返回格式与长期项目格式是否明确区分？
  10. 失败时能否定位到具体对象、字段和来源版本？
  11. 更换供应商是否只影响适配器与任务，而不是故事主数据？
  12. 仓库实际执行了什么，又有哪些只是 README 或提示词中的承诺？

彻底理解一个生成系统，不是知道每个按钮调用了哪个函数，而是能解释：哪些决定来自故事，哪些由导演新增，哪些只是供应商要求；它们怎样被保存、验证、转换、执行，又怎样在修改后可靠地重新计算。
