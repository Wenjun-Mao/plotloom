# Plotloom development contract

- Fix root causes and contracts rather than symptoms; preserve regression coverage for current supported behavior.
- Breaking changes and targeted development-data resets are the preferred default. Do not add or retain backward-compatibility layers, historical replay support, or automatic backups unless explicitly required. Remove obsolete code and tests with retired contracts; prefer the smallest current-contract implementation.
- Keep resets and deletions scoped to identified disposable data. Preserve current user-valued assets and work unless their removal is explicitly authorized; retain credential protection, transaction integrity, and unknown-dispatch safety. This policy does not authorize broad deletion or removal of current product features such as snapshot/restore.
- Keep credentials out of project state, persistence, logs, traces, and public settings.
- Development/test generation through Codex ImageGen and the owner's H3 gateway is pre-authorized; no per-call user approval is needed. Use bounded experiments and preserve dispatch safety. Other providers or paid fallbacks require explicit approval; generation authority does not imply creative acceptance or deletion authority.
- When the owner authorizes specialist coordination for a run, routine follow-ups and safe continuation of the same frozen job in the existing specialist task are covered; do not ask again merely because a known preflight blocker was repaired. Preserve package, model, settings and dispatch identity; first verify completion/pin/job state to prevent duplicate execution. User-directed stops, safety/permission refusals and material scope changes are not automatically resumable. See ADR 0131.
- Preserve the extraction boundary: production code must not import or read Narrative Forge V1 runtime paths or data.
- Record durable changes to public APIs, prompt/schema contracts, persistence, runtime behavior, or workflow semantics as concise ADRs.
- Keep generated frontend assets in `src/plotloom/static/` fresh whenever `frontend/` changes.
- Use `uv` and checked lockfiles. Follow the development-verification policy below.

## Development verification (required)

- During development, use `quick` (fast) for general feedback, `focused` for exact test cases, and `module` for reviewed product-owner selections. Reserve `full` for the stable final release candidate; do not run it, or an equivalent collection of all release gates, after each edit or routine review.
- **Quick / fast:** `uv run --locked --no-sync python scripts/verify.py quick`. This is fast feedback, not backend, browser or release acceptance.
- **Focused:** `uv run --locked --no-sync python scripts/verify.py focused` with explicit `--pytest`, `--vitest` and/or `--playwright` selectors. Choose cases from the changed contract and its affected consumers, including regression checks; the runner does not infer coverage from changed files.
- **Module:** use `uv run --locked --no-sync python scripts/verify.py module --module NAME --depth contract` and choose `contract`, `browser` or `complete` for the affected scope. `contract` selects pytest and Vitest owners, `browser` selects Playwright journeys, and `complete` selects every nonempty suite for the owner plus gates declared in `scripts/testing/module-ownership.json`. Multiple `--module` values form one deduplicated union. Add `--show` to print the expanded selectors, shared dependencies, gates and exact commands without running checks. Module runs first verify the full native owner union and refuse ambient filters; module success remains scoped evidence, not full release qualification.
- **Risk-scoped local qualification:** A bounded frontend presentation/navigation change that consumes unchanged APIs may use local frontend qualification instead of the full local suite. First review the actual diff and dependency surface against a trusted revision; record why backend/API schemas and request payloads, persistence, admission, auth, provider/prompt behavior, dependencies, build tooling and package contracts are unchanged. Frontend file paths alone are not enough. Run the unfiltered frontend unit suite and both type checks, deterministic asset generation and a second-build SHA-256 tree comparison, plus explicit affected browser regressions and desktop pixel inspection. Run affected shared-contract or package checks when the actual diff warrants them. This is not a new `verify.py` tier.
- **Final full gate:** `uv run --locked --no-sync python scripts/verify.py full` remains required for changes to those contracts or dependencies, broad refactors, cross-layer runtime changes, or uncertain impact. It is also the complete local release candidate gate when the scope calls for it. Local frontend qualification does not mean full local release qualification, hosted CI success, or product acceptance.
- **Evidence reuse and hosted CI:** Coordinate one owner for full qualification. Reuse evidence while its source, dependency and configuration inputs remain unchanged; rebuilding generated frontend assets alone does not invalidate passed backend integration evidence. After a failure, diagnose it and rerun the failed and downstream affected checks, invalidating prior evidence only for inputs that changed. Repeat `full` only when material changes invalidate its evidence or a diagnosed failure requires requalification, and state the reason. Required unfiltered hosted CI remains separate and must not be filtered, waived, or described as passed until it passes.
- If a check fails, diagnose the cause and iterate with the smallest relevant checks before returning to the final gate. Do not bypass failures, weaken assertions or shrink release coverage to save time.
- For documentation-only edits that do not affect executable behavior, check the diff and consistency of documented commands; do not manually rerun the full suite solely for those edits.
- Report the tier, explicit selections, results, qualified revision and remaining gaps. See `docs/development.md` for prerequisites, command examples and the gates included in each tier.

## Bounded delivery

- Before a generation-contract fix, identify which fields the author, model, and trusted code own. Check primary prompt, response schema, binder, and validator agreement before adding correction machinery. Amend the relevant ADR before changing ownership; do not rewrite retained evidence to imply it satisfied a newer contract. Old contracts need not remain executable.
- Keep approved scope, phase-specific instructions and progress in the roadmap, not this file. Start at `docs/roadmap/README.md`; each assignment must identify its approved step, deliverable, evidence, exclusions and stopping condition.
- Use one source owner by default. Follow Relay's Manager model choice guide for all delegation: GPT-6 Luna / Max for clear bounded implementation, routine coordination or focused verification; GPT-6.1 Sol / Medium for challenging coding/integration with meaningful ambiguity; GPT-6.1 Sol / High for difficult architecture, high-risk decisions or persistent reasoning failures. Choose by difficulty, not role or an automatic escalation ladder; explicit user choices take precedence. Set supported native model/effort fields explicitly, announce the actual choice, and disclose unavailable or inherited settings. Reserve Astra for demonstrated need or user request. Do not change active tasks or global defaults. See ADR 0023.
- Keep briefs bounded with minimal history. Use an independent review on a stable candidate; reopen only for concrete findings or material changes. Do not leave delegated work without a supported completion-reporting path.
- Fix demonstrated blockers within scope; defer optional improvements. A review finding is not authorization to expand scope. Material changes to the approved outcome, acceptance, risk or authority require user agreement before implementation.
- After two unsuccessful attempts at the same acceptance criterion, preserve the evidence and reassess the cause and method before dispatching again. Explain the adjustment; do not repeat the same broad assignment or build more tracking machinery instead of delivering the outcome.
- At the end of a completed, verified implementation, merge the scoped changes back to `main` and push to `origin` by default, unless the user explicitly requests otherwise. Check remote divergence and preserve unrelated work; never force-push or bypass failed gates. Report the pushed revision and any pending CI separately from local verification.
- Long-running jobs should report completion/failure through the existing task/job mechanism. Avoid frequent model-driven polling, repeated inventory calls, and unchanged status narration. Keep searches and output targeted; exclude generated assets unless they are the subject of the task.
- Report implementation, executed verification and product acceptance separately, with revision/worktree state, remaining gaps and next action. Test counts and worker reports alone do not establish acceptance. Include usage/cost deltas only when available from existing records; do not invent measurements.
