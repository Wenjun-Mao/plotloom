# ADR 0127: Reusable creator lifecycle acceptance

Status: Accepted workflow decision, 2026-10-07. Product capabilities and each run's
execution authority remain separately approved in the roadmap.

## Problem

A successful new-story path and software test totals do not establish safe
mid-project revision, media regeneration, recovery or visual usability. Separate
one-off walkthrough plans can diverge and lose regressions from previous findings.

## Decision

Maintain the existing graph-workbench-acceptance document as ONE reusable creator
lifecycle playbook with stable C/P/E identities and Create → Revise → Recover
rounds. Each major update starts from that base with a scoped roadmap run profile
and a dated verification ledger, not a second acceptance checklist.

Profiles declare the candidate/loaded environment, changes, disposable data,
protection, prerequisites, authority, selected scenarios and omissions. They may
adapt emphasis and bounded generation effort but cannot relax required gates or
promote older evidence, fake delivery or API-seeded state into a new native/UI PASS.
Unknown or unexercised required behavior remains PARTIAL/NOT EXERCISED.

Creation establishes a completed baseline. Revision modifies that SAME project
and verifies affected dependencies, preserved unrelated work, explicit rebuilds
and revised-route playback using actual artifact identities/hashes. Recovery uses
exact disposable targets and distinguishes simulated faults from actual failures.
Software qualification, native functional acceptance and author creative/media
quality approval remain separate conclusions.

## Alternatives and consequences

Reject three independently maintained plans and restarting every walkthrough from
scratch: both lose cross-stage revision evidence. Reject mandatory new provider
generation for every cosmetic update; the profile must state what was and was not
requalified. Existing required C/P checks and release gates remain unchanged.

Reusable failures are captured in the run ledger, reviewed, then promoted to the
owning check. Remove a check only when its product contract is formally retired.
Adopting this procedure does not implement the current first-install-only gap,
wire intent generation, dispatch/continue specialist jobs or authorize deletion.
