Narrative Forge：数据契约、损失与重构接缝

工作流告诉你数据怎样移动，契约才告诉你系统真正相信什么。本章把 project v6 拆到字段、ID、引用、持久化、提示词、密钥和校验边界，再判断哪些设计值得保留，哪些信息必须在重写前补回来。

本章的阅读姿势

  • 带“源码实现”的句子都给出相对路径和函数或字段。
  • 测试约束单独列出，不把“有测试”写成“创作质量已验证”。
  • 缺陷判断用“分析推论”，未来设计用“重构建议”，不冒充作者意图。

一、契约基线与归因边界

源码实现 本章绑定本地 24c3c47。创作模型与大部分媒体/导出能力可在原作者历史快照 abebc29 中追溯；首次启动、根目录 .env、session-only API key 和供应商配置清洗来自 fork 修复 a9513b5；默认端口与本地顺延来自尚未推到 origin/main 的 24c3c47。证据定位：git log abebc29..24c3c47；git diff --stat abebc29..24c3c47。

uv 不是这里的数据架构

源码实现 6b4972f 增加了 pyproject.toml、uv.lock 和空包脚手架，但实际服务入口仍是仓库根部 app.py 的 main()。证据定位：app.py · main()；pyproject.toml · 项目元数据。

分析推论 因而本章不把用户为依赖管理建立的 uv 工程视为原作者领域模型，也不从脚手架推导不存在的包式服务架构。

scene 不是本手册定义的“场”

分析推论 因而跨系统建模时应把这个对象映射为 ShotRecord 或现有镜头记录，而不是 NarrativeScene；否则会把“控制室这一场戏”和“控制室里的八个镜头”合成同一层。

四、episodes 与 façade：怎样在不重写旧模块的情况下加入分集

源码实现 迁移器把 meta.mode === "serial" 或任一旧 scene 的 episode > 1 判为短剧旧数据。只有 episodes 尚不是数组且旧 scenes 非空时，它才按 scene.episode 分组建集；否则旧 scenes 进入互动容器或沿既有 episodes 规范化。完成后删除旧顶层 scenes/start/selected 字段。证据定位：static/src/episode-model.js · migrate()。

源码实现 installFacade() 再用访问器创建 project.scenes、project.startSceneId 与 project.selectedSceneId：互动模式转发到 interactive，短剧模式转发到当前 episode。属性描述没有设置 enumerable，所以它们不会进入 JSON.stringify(project)。证据定位：static/src/episode-model.js · activeContainer()/installFacade()。

分析推论 这是一个有效的渐进兼容接缝：旧编辑代码继续写 project.scenes，持久格式却保持 interactive/episodes 的新拓扑。代价是属性含义依赖全局 meta.mode 和 selectedEpisodeId，函数若在错误模式下运行，读到的“同名 scenes”会是另一份集合。

重构建议

重构第一步不必删除 façade。先把隐式全局访问收口成 activeShotContainer(project, mode, episodeId)，让调用者显式带上下文；等测试覆盖稳定后，再逐模块取消 project.scenes 访问器。

引用完整性不是统一的一道门

源码实现 删除镜头时，事件处理器清理指向该 ID 的 nextSceneId、选择目标、起点与 referenceSceneId；拖动镜头只更新显示顺序，不改互动连接。证据定位：static/src/events.js · 删除镜头 click handler；static/src/project-model.js · moveSceneRelative()；static/src/scene-list.js · bindSceneDrag()。

源码实现 删除角色卡或场景卡时，面板只从项目级数组移除卡片并保存，没有遍历 scenes 清理对应 characterIds 或 sceneCardId。证据定位：static/src/render.js · renderCharacterPanel()/renderSceneCardPanel() 的删除处理器。

分析推论 这会允许孤儿卡片引用留在项目 JSON 中；提示编译时找不到卡片会悄悄忽略，而不是报告引用损坏。重写时需要统一的引用完整性层，而不是给每个删除按钮各写一套清理。

月城案例

镜 07 的故事事实是“机械旁路失败”；角色卡规定阮星服装和铜钥匙，场景卡规定红色应急灯与左金右青空间轴，镜头规格规定中景和人物退半步。理想编译器应能说明每一行提示来自哪个字段；当前项目只保存最终字符串，日后很难回答“火花是导演输入、模板补充还是模型自己加的”。

八、供应商设置与密钥：优先级和持久化必须分开看

公开设置的优先级

源码实现 服务端读取 projects/_provider_config.json 后，用宿主环境或根目录 .env 中的 Base URL、模型与 provider 选择覆盖文件值；由于 dotenv 使用 override=False，宿主环境优先于 .env。证据定位：app.py · load_root_environment()/_env_provider_overrides()/get_provider_config()。

源码实现 浏览器启动时按“内置默认值 → 本地公开缓存 → 服务端返回”合并；Test 与 Generate 调用 providerSettings() 前会把可见表单同步进内存，所以无需先点击“保存供应商设置”。证据定位：static/src/provider-config.js · loadProviderConfig()/syncProviderConfigFromForm()/providerSettings()。

秘密的优先级

浏览器当前会话手输 key→ 该类服务端环境 key→ ATLASCLOUD_API_KEY 兜底→ 无 key：请求失败

源码实现 浏览器手输 key 只存 sessionStorage，通过当前生成请求的 JSON 字段或轮询 header 送到自己的 Python 服务；若字段为空，provider_api_key() 先找种类专用环境变量，再找 AtlasCloud 兜底。证据定位：static/src/provider-config.js · _saveSessionSecrets()/providerSettings()；static/src/api.js · generateImage()/generateVideo()/pollPrediction()；app.py · provider_api_key()/api_prediction()。

源码实现 GET provider config 只返回公开字段和三类 key 可用性布尔值；POST 若字段名规范化后等于或以 apikey 结尾就拒绝。加载旧配置时只保留白名单公参，并尽力重写清洗后的文件。证据定位：app.py · is_provider_secret_field()/sanitize_provider_config()/_load_provider_config_file()/get_provider_config()/save_provider_config()。

“只存在 sessionStorage”不是端到端秘密保证

源码实现 API key 仍会从浏览器发送到服务端生成端点或 prediction header；路由表与 DirectorHandler 没有身份验证中间层。平台 PORT 模式默认监听 0.0.0.0。证据定位：static/src/api.js · provider request fields/headers；backend/route_registry.py · API_ROUTES；app.py · do_GET()/do_POST()/resolve_server_address()。

分析推论 session-only 解决的是浏览器和项目文件的持久化泄露，不解决未认证远程部署的访问控制，也不代替 HTTPS。远程实例应保持私有；若要公开访问，认证与传输安全必须作为独立工程加入。

一个已经发生的数量语义漂移

源码实现 互动模式的 draftRequestMeta() 已把 nodeCount 定义为 storyNodeCount × shotsPerNode，但 generateStoryDraft() 为“大规模生成”二次确认计算 totalShots 时又乘了一次 interactiveShotsPerNode，提示文案还把这个 nodeCount 称为“剧情节点”。证据定位：static/src/draft.js · draftRequestMeta() 返回值与 generateStoryDraft() 的 totalShots。

分析推论 多镜节点时，二次确认会高估镜头量；真正发送给后端的树参数、后端 240 上限和安装器 expectedNodes 仍沿用第一次算出的正确总镜数。根因不是乘法本身，而是变量 nodeCount 从“剧情节点数”漂移成“总镜数”后，调用方仍按旧语义使用。

重构建议 用不可混淆的 storyNodeCount、shotsPerNode 与 totalShotCount 三字段贯穿估算、请求和安装契约，并为每一层断言 totalShotCount = storyNodeCount × shotsPerNode。

十一、当前强项与信息损失

分析推论 值得保留

强项

  • 互动与短剧共享一套镜头编辑、媒体任务和播放能力，分集 façade 使演进成本可控。
  • 角色卡、场景卡、参考镜头与首尾状态已经把“连续性”从一句全局风格提示推进到可引用数据。
  • 供应商 adapter 把协议差异收口为提交/轮询契约；同步图片也能复用同一前端状态机。
  • 浏览器项目、服务端项目文件、资产文件和发布包各有明确操作，恢复快照与备份降低覆盖风险。
  • fork 修复后的密钥边界把公参与秘密分开，并给 Test/Generate 当前表单即时生效。

分析推论 重写前要补

信息损失

  • 没有独立的剧集场次与叙事节拍实体；action 同时承担可见事件、节拍摘要和部分场次语义。
  • 没有镜头目的、覆盖节拍、机位、角度、运动、构图、声音、切点理由与故事板 panel 的规范字段。
  • 模型临时 key 在安装后丢失，生成来源、提示模板版本、响应原文和人工改动历史也没有共同 provenance。
  • 角色/场景关联由名字匹配推断；返回 JSON 没有逐镜明确 card ID，卡片删除又可能留下孤儿引用。
  • scene 同时承担导演规格、生成提示、任务状态和资产地址，导致“改镜头”与“重跑任务”的边界模糊。
  • 作者时长与供应商运行时档位共用一个 duration；短剧最终导出实际又以媒体文件时长为准。

十二、适合渐进重构的接缝

重构建议 不要从“重新做一个页面”开始。先沿现有模块边界把隐含契约变成显式接口，再逐步替换内部模型。

1. Schema 适配层

重构建议 保留 normalizeProject() 为入口，但让它只负责 v6 JSON ↔ canonical model。新增版本化 schema 与引用校验，不让 UI 直接承担迁移。

2. 叙事主数据

重构建议 新增 Episode → DramaticScene → Beat，再让 Shot 通过多对多链接认领 Beat；保留现有 scene 作为过渡 ShotRecord。

3. 安装器边界

重构建议 把两个 installGenerated* 改为纯适配器：先验证模型传输 schema，保存原始 response/provenance，再生成领域命令，不直接改全局 project。

4. Prompt 编译器

重构建议 将模板版本、结构化输入、供应商能力、编译结果和人工覆盖分开；用依赖哈希标记提示是否过期。

5. 任务与资产仓库

重构建议 把 prediction/job/attempt 从 scene 拆成 GenerationTask，把 URL/path/checksum/媒体属性拆成不可变 Artifact；Asset 只保留角色、地点、道具或长期参考物的逻辑身份，并指向被批准的 Artifact revision。Shot 只引用所选逻辑资产或具体输入 Artifact。

6. 导出适配器

重构建议 继续保留 backend/publishing.py 与 backend/serial_exporting.py 的独立出口，但让它们只消费经过验证的 ReleaseManifest，而不是任意 project dict。

渐进重构的停线规则

重构建议 每一步都先证明现有 v6 项目仍可导入、编辑和导出，再让新数据成为某一条路径的权威。不要同时重写项目模型、提示词、供应商协议和播放器；那会失去判断回归来自哪一层的能力。

本章结论：把它当作可演进的生产原型，而不是最终领域模型

分析推论 Narrative Forge 当前最成熟的是“镜头记录驱动的生成工作台”：它能让一条记录贯穿文本草案、提示组合、图片、视频、预览和发布。这个垂直切片很有价值，说明项目并非未完成的 UI 空壳。

分析推论 它的主要限制也正来自同一便利：scene 过度聚合，创作过程中的场、节拍、镜头理由、故事板和生成版本没有成为一等数据。若你的目标是“彻底理解后按自己需求重写”，最稳妥的路线是保留已有 adapter、导出器和可用 UI，先在中间补一个供应商无关、可追踪、少损失的核心模型。
