## Owning diagnosis and scope

Before editing, identify the presentational root causes in the shared CSS,
component hierarchy and view composition. Existing style layers override earlier
roles, while nested bordered groups, repeated instruction cards and technical
actions compete with the creator's current task. Treat this as a coherent
visual-system repair, not an appended cascade of page-specific overrides or a
global font-size shrink. Keep critical instructions, errors and next actions
visible; optional detail can use compact help or an explicit disclosure.

Cover the existing shell/onboarding/project directory, Brief/settings and
presets, Source/candidate/accepted reports/branches, character/art/reference
views, script/storyboard/production/media review, reader/player and professional
tools. Shared primitives should carry the design consistently; narrative and
technical views may have intentional typography appropriate to their role.

Use the side-inspector preference where existing node/detail views support it:
the detail editor remains reachable while browsing a long graph. Keep focus,
selected identity and unsaved input stable. Do not introduce a new graph editor
or claim that a short sample proves long-graph usability.

Help uses a small, label-aligned ⓘ with an adequate interaction target, clear
focus and the existing hover/focus/tap/Escape semantics. Apply the hierarchy
throughout, not just to that one control. Both future workbench views should
share this visual quality; more controls do not imply more visual clutter.
