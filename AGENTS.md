# Plotloom development contract

- Fix root causes and contracts rather than symptoms; preserve regression coverage for current supported behavior.
- Breaking changes and targeted development-data resets are the preferred default. Do not add or retain backward-compatibility layers, historical replay support, or automatic backups unless explicitly required. Remove obsolete code and tests with retired contracts; prefer the smallest current-contract implementation.
- Keep resets and deletions scoped to identified disposable data. Preserve current user-valued assets and work unless their removal is explicitly authorized; retain credential protection, transaction integrity, and unknown-dispatch safety. This policy does not authorize broad deletion or removal of current product features such as snapshot/restore.
- Keep credentials out of project state, persistence, logs, traces, and public settings.
- Development/test generation through Codex ImageGen and the owner's H3 gateway is pre-authorized; no per-call user approval is needed. The owner's prospective budget default is unlimited unless he specifies a finite cap; do not invent cumulative image/job/requested-seconds ceilings or ask for routine budget increases within approved work. Use the smallest relevant experiments and preserve dispatch safety, finite task outcomes and provider/account constraints. Existing frozen finite grants remain enforced until a prospective contract/grant explicitly supports the new default; never bypass them or rewrite their evidence. Other providers or paid fallbacks require explicit approval; generation authority does not imply creative acceptance or deletion authority. See ADR 0198's prospective-budget amendment and ADR 0200 for nullable aggregate budget contracts.
- When the owner authorizes specialist coordination for a run, routine follow-ups and safe continuation of the same frozen job in the existing specialist task are covered; do not ask again merely because a known preflight blocker was repaired. Preserve package, model, settings and dispatch identity; first verify completion/pin/job state to prevent duplicate execution. User-directed stops, safety/permission refusals and material scope changes are not automatically resumable. See ADR 0131.
- The owner delegates material generation/inspection, testing accept/reject decisions, clip selection, native-audio review and E2E completion for explicitly scoped disposable QA projects. Record these as agent-operated QA under delegated authority, never as the owner's personal review. The current bounded grant is ADR 0198; keep its two-H3-submission/ten-requested-second cap. This grants no authority over real stories, larger budgets, other providers, uncertain-dispatch clearing or GitHub CI. Authorization is not evidence of inspecting unseen outputs.
- Preserve the extraction boundary: production code must not import or read Narrative Forge V1 runtime paths or data.
- Record durable changes to public APIs, prompt/schema contracts, persistence, runtime behavior, or workflow semantics as concise ADRs.
- Keep generated frontend assets in `src/plotloom/static/` fresh whenever `frontend/` changes.
- Use `uv` and checked lockfiles. Follow the development-verification policy below.
- **GitHub Actions/CI is OFF by default.** A new explicit request directly from Wenjun is required before starting, dispatching, rerunning, retrying or knowingly triggering a run, including filtered/diagnostic runs and automatic triggers from pushes. Manager approval, implementation requests, repository defaults and ordinary push authority are not substitutes. Stay within the directly requested scope; a failed run is not retry authority. CI preparation, workflow drafts and publication of CI changes remain on hold until that direct request; do not substitute new automations/watchers or disable workflows/add skip markers to evade this boundary.
- **Hosted CI is not a release requirement.** GitHub Actions or another hosted runner is optional, not a prerequisite for a stable/general-availability release. Do not report an unrequested hosted run as a pending release blocker. Required local qualification, exact-package installation checks, real supported-workflow evidence and applicable acceptance remain; a concrete unresolved defect discovered anywhere still needs resolution. Preserve historical failed results as failed. See ADR 0199, which supersedes older mandatory-hosted-CI wording.

## Small real E2E first (required)

- **Define the smallest observable outcome before implementation.** Name one user journey, the smallest valid fixture, intended runtime/provider, bounded resource/cost limits, success evidence and cleanup/settlement owner. For batch work, prove the smallest valid batch before scaling to the full inventory. Keep this brief in the existing plan; do not build a new tracking system.
- **Resolve live-test prerequisites early.** Check supported schema/data, fixture currentness, required human review, credentials/access and safe dispatch authority before broad implementation or qualification. Identify a compatible test fixture before a schema-breaking reset removes the only usable one; do not add a migration or backup merely to retain incompatible disposable data. If the fixture or authority is unavailable, state the exact E2E blocker and minimum user action at the outset. Never fabricate consent, creative approval or provider outcomes.
- **Attempt the vertical slice before broad qualification.** After focused safety/contract checks pass, exercise real UI/API, persistence and the intended runtime/provider through an observable output and readback using the smallest authorized fixture. Fakes are useful for development and unsafe failure paths, but do not substitute for the real journey. Do not postpone this checkpoint until every unrelated suite or infrastructure issue is repaired. If blocked, report that explicitly while continuing independent authorized work; do not call the feature E2E-complete. This checkpoint does not waive final release gates or human creative acceptance.
- **Preflight the execution envelope before expensive runs.** Use small existing probes for source/dependency identity, platform/runtime versions, actual CLI interpreter selection, required permissions/receipts/imports and service/provider readiness. Label material reproduction differences, such as architecture or Python patch version, before interpreting a local pass. Keep credentials private. Reuse a validated envelope until relevant inputs change; do not create another runner or provisioning framework for routine diagnosis.
- **Keep infrastructure repair off the product path unless it actually blocks it.** Classify each failure as product behavior, test fixture, environment, deployment or unrelated infrastructure. State why it blocks the small real journey or a required release claim. Repair demonstrated in-scope blockers with the smallest causal check; surface unrelated work separately and obtain approval for a material scope expansion. After a bounded infrastructure repair, return to the product outcome or name its remaining blocker instead of chaining supporting-tool checkpoints.
- **Use the least-powerful applicable lifecycle operation.** Inspect supported operation contracts first: ordinary idle deletion, abandonment/revocation and unresolved remote work have different prerequisites. Check the applicable native path before investigating guard changes or historical process identities. Revalidate exact targets, authority and quiescence; never bypass guards, signal unrelated processes or clear UNKNOWN reservations to manufacture progress.
- **Give qualification one execution owner.** Independent reviewers inspect a stable diff and retained evidence; manager retests target concrete uncertainty or changed inputs rather than automatically repeating the worker's selection. Reuse unchanged evidence. Before another expensive run, state the diagnosed cause, changed inputs and expected new information. Retain actionable failure context from the first failure without exposing secrets or weakening assertions; after two unsuccessful attempts, reassess the method before another run.
- **Report product progress, not just verification activity.** Separate small real E2E, scale/performance, local qualification, hosted qualification, activation and human acceptance. At a checkpoint state the last real outcome, exact remaining blocker, next smallest action and known time spent on product work, infrastructure, execution/waiting and coordination; mark unavailable timings rather than inventing percentages. Test totals, visible controls and health checks do not establish provider E2E. Routine in-scope checkpoints are not new owner-approval gates.

See ADR 0023 for the rationale. These rules prioritize early product evidence without weakening dispatch safety, data integrity, current user authority or release acceptance.

## Development verification (required)

- During development, use `quick` (fast) for general feedback, `focused` for exact test cases, and `module` for reviewed product-owner selections. Reserve `full` for the stable final release candidate; do not run it, or an equivalent collection of all release gates, after each edit or routine review.
- **Quick / fast:** `uv run --locked --no-sync python scripts/verify.py quick`. This is fast feedback, not backend, browser or release acceptance.
- **Focused:** `uv run --locked --no-sync python scripts/verify.py focused` with explicit `--pytest`, `--vitest` and/or `--playwright` selectors. Choose cases from the changed contract and its affected consumers, including regression checks; the runner does not infer coverage from changed files.
- **Module:** use `uv run --locked --no-sync python scripts/verify.py module --module NAME --depth contract` and choose `contract`, `browser` or `complete` for the affected scope. `contract` selects pytest and Vitest owners, `browser` selects Playwright journeys, and `complete` selects every nonempty suite for the owner plus gates declared in `scripts/testing/module-ownership.json`. Multiple `--module` values form one deduplicated union. Add `--show` to print the expanded selectors, shared dependencies, gates and exact commands without running checks. Module runs first verify the full native owner union and refuse ambient filters; module success remains scoped evidence, not full release qualification.
- **Risk-scoped local qualification:** A bounded frontend presentation/navigation change that consumes unchanged APIs may use local frontend qualification instead of the full local suite. First review the actual diff and dependency surface against a trusted revision; record why backend/API schemas and request payloads, persistence, admission, auth, provider/prompt behavior, dependencies, build tooling and package contracts are unchanged. Frontend file paths alone are not enough. Run the unfiltered frontend unit suite and both type checks, deterministic asset generation and a second-build SHA-256 tree comparison, plus explicit affected browser regressions and desktop pixel inspection. Run affected shared-contract or package checks when the actual diff warrants them. This is not a new `verify.py` tier.
- **Final full gate:** `uv run --locked --no-sync python scripts/verify.py full` remains required for changes to those contracts or dependencies, broad refactors, cross-layer runtime changes, or uncertain impact. It is also the complete local release candidate gate when the scope calls for it. Local frontend qualification does not mean full local release qualification, hosted CI success, or product acceptance.
- The full Python step collects the native suite and runs two dynamically balanced whole-file pytest processes with separate temporary roots. It refuses ambient pytest filters, prints each worker report, cleans up worker process groups on SIGTERM or interruption, and fails if either worker fails; focused and module selectors remain native single-process runs.
- **Evidence reuse and optional hosted CI:** Coordinate one owner for full qualification. Reuse evidence while its source, dependency and configuration inputs remain unchanged; rebuilding generated frontend assets alone does not invalidate passed backend integration evidence. After a failure, diagnose it and rerun the failed and downstream affected checks, invalidating prior evidence only for inputs that changed. Repeat `full` only when material changes invalidate its evidence or a diagnosed failure requires requalification, and state the reason. Hosted qualification is optional and never implicit authority to run CI. Without Wenjun's direct request, record it as not requested/not run, not a release blocker; retain any prior failure as failed. If explicitly requested, report the actual scope and outcome: filtered diagnostics are not complete hosted qualification, and failed, skipped or cancelled checks are not passes.
- If a check fails, diagnose the cause and iterate with the smallest relevant checks before returning to the final gate. Do not bypass failures, weaken assertions or shrink release coverage to save time.
- For documentation-only edits that do not affect executable behavior, check the diff and consistency of documented commands; do not manually rerun the full suite solely for those edits.
- Report the tier, explicit selections, results, qualified revision and remaining gaps. See `docs/development.md` for prerequisites, command examples and the gates included in each tier.

## Bounded delivery

- Before a generation-contract fix, identify which fields the author, model, and trusted code own. Check primary prompt, response schema, binder, and validator agreement before adding correction machinery. Amend the relevant ADR before changing ownership; do not rewrite retained evidence to imply it satisfied a newer contract. Old contracts need not remain executable.
- Keep approved scope, phase-specific instructions and progress in the roadmap, not this file. Start at `docs/roadmap/README.md`; each assignment must identify its approved step, deliverable, evidence, exclusions and stopping condition.
- The owner gives standing approval to create separate Relay worker chats for approved repository assignments; do not request fresh chat-creation approval for each worker. Select and announce model/reasoning under the guide below, use the retained checkout for serial work, register completion reporting and reuse the worker for in-scope follow-ups. This approval does not expand implementation scope, override native permissions or authorize concurrent source writers.
- Use one source owner by default. Follow Relay's Manager model choice guide for all delegation: GPT-6 Luna / Max for clear bounded implementation, routine coordination or focused verification; GPT-6.1 Sol / Medium for challenging coding/integration with meaningful ambiguity; GPT-6.1 Sol / High for difficult architecture, high-risk decisions or persistent reasoning failures. Choose by difficulty, not role or an automatic escalation ladder; explicit user choices take precedence. Set supported native model/effort fields explicitly, announce the actual choice, and disclose unavailable or inherited settings. Reserve Astra for demonstrated need or user request. Do not change active tasks or global defaults. See ADR 0023.
- Keep briefs bounded with minimal history. Use an independent review on a stable candidate; reopen only for concrete findings or material changes. Do not leave delegated work without a supported completion-reporting path.
- Fix demonstrated blockers within scope; defer optional improvements. A review finding is not authorization to expand scope. Material changes to the approved outcome, acceptance, risk or authority require user agreement before implementation.
- After two unsuccessful attempts at the same acceptance criterion, preserve the evidence and reassess the cause and method before dispatching again. Explain the adjustment; do not repeat the same broad assignment or build more tracking machinery instead of delivering the outcome.
- At the end of a completed, verified implementation, preserve a coherent scoped checkpoint on `main`. Normal publication remains subject to user authority and the CI-off rule: do not push if it would trigger GitHub CI without Wenjun's new explicit request. Hold publication and report the local revision instead; do not alter workflows or use skip markers as a workaround. Before an authorized push, check remote divergence and preserve unrelated work; never force-push or bypass failed gates. Report publication and any explicitly requested CI separately from local verification.
- Long-running jobs should report completion/failure through the existing task/job mechanism. Avoid frequent model-driven polling, repeated inventory calls, and unchanged status narration. Keep searches and output targeted; exclude generated assets unless they are the subject of the task.
- Report implementation, executed verification and product acceptance separately, with revision/worktree state, remaining gaps and next action. Test counts and worker reports alone do not establish acceptance. Include usage/cost deltas only when available from existing records; do not invent measurements.
