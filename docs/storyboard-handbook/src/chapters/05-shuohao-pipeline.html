shuohao-skills：五段管线怎样接力

这不是一个“按按钮自动跑完”的制片应用，而是一组交给编码代理执行的工作规程，加上一套不调用模型的确定性 Node 工具。理解它的关键，是把谁负责创作、谁负责搬运事实、谁负责判错分开。

读完本章，你应该能回答

  • 五份 JSON 各自决定什么，哪些字段会成为下一层的事实。
  • seed、validate、render、export 为什么不是“AI 创作”。
  • C / S / P / B 编号在哪里稳定，在哪里已经退化成名字、类型或数组位置。
  • README 和 SKILL 的设计声明，与固定提交中的源码及测试究竟是否一致。

一、先定证据口径：这是静态审计，不是运行测评

文档声明 根 README 把项目定义为供 Claude Code 或 Codex 使用的 AI 短剧 skill 集合；每个 skill 由给代理阅读的 SKILL.md、标准库脚本、自测、参考资料、样例和截图组成，并声称 Node 18 以上即可、不需要 npm 安装或 API key。

源码实现 五个主脚本在文件头只导入 node:fs、node:path、node:url 等标准库；创作工作则写在 Markdown 指令中，由当前会话里的代理完成。脚本没有实现小说理解、人物塑造、剧本写作或镜头审美模型调用。

测试约束 每个 skill 都有独立 scripts/selftest.mjs，测试文件直接导入纯函数、构造夹具并击穿质量门。仓库文档声明这些自测不调用模型；本手册只审阅了测试源码，没有执行第三方脚本，因此本章不使用“运行验证”标签。

证据入口：shuohao-skills README.md 第 9–23、102–137 行；五个 skills/*/scripts/*.mjs 的 import 区；五个 skills/*/scripts/selftest.mjs（固定提交 4322897e6d2bdaf66365534fd40194360c75a85f）。

“零依赖”不等于“没有运行时”

分析推论 这里准确的说法是“没有 npm 包依赖”：仍需 Node 18+，仍需能读写文件的代理环境；可选出图还依赖 Codex 的内置图像能力。把它理解成完全离线的单体程序，会误判系统边界。

二、五段是交付顺序，标准 seed 主干其实是一张 DAG

文档声明 项目把五份交付物概括为“大纲决定什么、角色决定谁、美术决定哪里和道具、剧本决定戏、分镜决定怎么拍”。根 README 同时强调：大纲先收敛结构，角色、美术与剧本可以同步迭代，分镜位于消费端。

源码实现 图中没有画完所有可选边：剧本可拿 art 做场景、光照、道具校验和展示；outline 提供角色显示名，cast 为剧本报告补 voice.prompt，也可成为代理写作上下文。它们不是 seedFromOutline() 建立剧本结构时的硬前提。

分析推论 因此“outline → characters → art → script → storyboard”适合作为人类的学习与交付顺序，却不是一条只能串行执行的函数链。角色与美术都从大纲分叉，后续再通过可选校验、写作上下文和报告展示汇合。

证据入口：根 README.md 第 11、15–23 行；scripts/report.mjs 的 PANES；skills/novel-script/SKILL.md Step 0–2；skills/novel-storyboard/scripts/novel-storyboard.mjs 的 loadCtx() 与 CLI main()。

三、每一段都有两台“引擎”：代理创作，脚本守合同

把整个仓库想成“创作台 + 质检台”最准确。代理读原文和参考指令，写出需要判断的内容；Node 脚本只做可重复的切块、搬运、计数、引用检查、格式检查和报告编译。

seed 的原则：搬事实，留设计

源码实现 四个下游 seed* 共享的原则是沿用上游已经拍板的事实，把本层应创作的数组或字符串留空；只有部分对象附临时上下文。角色 seed 留空画像与提示词；美术 seed 留空锚点与光照，且只有带 reusePlan 的场景获得 seedNote；剧本 seed 留空 scenes；分镜 seed 留空 segments 并固定携带 seedScenes。

分析推论 这是本仓库最值得复用的架构思想：不要让模型重新发明已经确认的编号、清单和时长。否则同一事实会在每一层被“再创作”一次，漂移很快变成必然。

五、稳定 ID 的真实边界：C、S、P 能接力，B 会换语义

通用方法 稳定 ID 的作用不是让表格好看，而是让名字修改、顺序调整和语言切换不会改变“它是谁”。审计这条管线时，不能只看字段像不像 ID，还要看下游是否继续引用同一个实体。

表 3　标识符从大纲到分镜的生命周期
编号 上游含义 下游如何使用 审计结论
C01 大纲人物实体。 剧本 scene.characters、台词 speaker、分镜 cut.characters 都继续用 C 码。 源码实现 主生产链稳定；但 cast 的 schema、内置样例与 validator 不要求 id。seedFromOutline() 会复制 C 码，却可能在后续手工/assemble 流程中成为无人守护的附加字段。
S01 大纲中的场景资产。 art 沿用为环境资产；script 每个场次用 sceneId 指向它；storyboard 不再存 S 码，而以 sceneIndex 指向该集 script 中的一次场景出现。 源码实现 S 码本身稳定，但“空间资产”和“剧情场次出现”是两种实体；分镜选择的是后者的数组位置。
P01 大纲拍板的叙事道具。 art 设计外观与状态；script 场次、storyboard cut 均继续引用 P 码并与上游集合对账。 源码实现 这是五段中最完整的稳定资产链。旧版 outline 没有 props 时，outline 的 refs 会移除道具检查并改标签，prop-cap 明示跳过；art 的四个 prop 门则因空数组直接通过，不统一显示“跳过”。
B07 大纲中的“爽点/爆点”实体，带类型、权重和落集。 script seed 把同集爽点的类型文本放进 beatsClaimed，不保留 B 码；script 的 flow 又产生另一种细粒度动作/台词“拍”；storyboard 用位置区间认领后者。 源码实现 “beat”在两层中同名不同义，B 码没有贯穿。两个同类型爽点落在同集时，beatsClaimed 的去重会进一步抹平个体。

核对入口：novel-outline/references/schema.md 的 C/S/P/B 结构；novel-characters.mjs 的 seedFromOutline() 与 validateCast()；novel-script.mjs 的 seedFromOutline()；novel-storyboard.mjs 的 expandScript() 与 seedFromScript()。

位置不是身份

分析推论 sceneIndex: 2 与 beats: [4, 6] 在当前文件版本内非常简洁；但在剧本前面插一场或一拍后，同一个数字就会指向另一件事。validate 能发现覆盖断裂，却不能自动知道旧镜头原本想指谁。

重构建议 如果要长期维护或多人协作，应给“场次出现”和“flow 节拍”独立稳定 ID；供应商适配时再派生 sceneIndex 与连续位置区间。

六、报告不是主数据，交接也不止一份 HTML

源码实现 五个 render 都从 JSON 生成 Markdown 或单页 HTML；报告内的“导出 JSON”嵌入的是源数据。根部 scripts/report.mjs 不是第六个 skill：它通过子进程调用每个 skill 的 render --html，再解决 CSS 选择器、页面脚本和图片相对路径冲突。

A

JSON · 主数据

下一层 seed、validate、render 读取它。修改应回到 JSON，不应把 HTML 当数据库。

B

Markdown / HTML · 评审面

给人看决策、KPI、质量门和台词/镜头表；随主数据重新渲染。

C

PNG · 可选视觉锚

角色、场景、道具和每切关键帧由代理调用图像能力生成；缺图时主流程仍可交付提示词与占位。

D

投产包 · 分镜专属

每个 segment 一个目录；export 写 prompt.md 与根部 manifest.json，并记录预期的 f1..fN.png 路径。PNG 必须事先位于目标路径，export 不生成也不复制它们。

文档声明 每阶段最后都要求向用户汇报数量、路径、未过的门、截断或未生成的图片。角色、美术和分镜的可选出图失败被设计为“跳过并明说”，不阻断纯文本交付。

分析推论 这使失败具有局部性：一张角色图失败，不必重写剧本；一份报告样式变化，不应改变主数据。不过，报告里显示的“全绿”只证明结构和规则通过，不能证明人物好看、对白动人或镜头有张力。

证据入口：五个 SKILL.md 的“输出与汇报”；根 README.md 第 33–54 行；scripts/report.mjs 的 PANES、splitDoc()、scopeCss() 与渲染子进程。

七、自包含是有意的重复，不是偶然的重复

源码实现 分镜脚本重新实现剧本的计秒规则，而不是跨目录 import novel-script；它也自己解析配方卡 frontmatter，而不是 import 外部 shot-recipes。源码注释明确给出的理由是：任一 skill 都应能单独拷走。

文档声明 根 README 对组合报告也采用同一原则：组装器调用各 skill 的渲染 CLI，不共享内部模板代码。这样某一 skill 改渲染时，组合报告重新调用即可获得新结果。

收益

  • 安装、复制、测试和故障边界都清楚。
  • 一个 skill 不存在时，其他 skill 仍能运行。
  • 外部卡库不成为分镜的硬依赖。

代价

  • 相同计时、枚举或解析规则会复制，版本漂移要靠测试发现。
  • 跨层契约不是一份正式 schema，而散落在 Markdown、源码和夹具里。
  • “可单独拷走”弱化了端到端迁移与版本兼容的显式管理。

分析推论 这是一个明确的架构取舍，不应简单重构成共享工具包。若未来改成平台型应用，可以抽出版本化领域契约；若仍以可搬运 skill 为产品形态，重复实现反而是部署隔离的一部分。

证据入口：novel-storyboard.mjs 第 175–224 行的 expandScript() 与卡库注释；根 README.md 第 35–49、110–129 行。

九、如果你要重写它，先保留这三条骨架

  1. 重构建议 保留“搬事实、留设计”的 seed 纪律。 上游已经批准的实体与约束只能引用，不能在下游再次生成。
  2. 重构建议 把 JSON 主数据、评审报告和供应商投产包分层。 报告可重建，供应商提示可再适配，主数据才是长期资产。

分析推论 shuohao-skills 的强项不是“模型替你写得多好”，而是把每层创作收进一个小合同，并用确定性脚本把可机械检查的错误挡在本层。它的主要技术债也来自同一选择：跨层正式 schema 不足、位置引用脆弱、文档在快速演进中留下旧术语。下一章将把最后一层 storyboard 拆到每个字段和每一道门。
