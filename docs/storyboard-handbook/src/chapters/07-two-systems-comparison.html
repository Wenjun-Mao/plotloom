第七章 · Comparative Systems

不是谁赢，而是谁保留了哪一种决定

Narrative Forge 把创作、预览、媒体生成和导出收进一个浏览器工作台；shuohao-skills 把小说改编拆成五份可校验、可交接的 JSON。两者解决的问题重叠，却不在同一抽象层。真正有用的比较，不是数功能按钮，而是沿同一条生产链追问：哪项决定被结构化保存，哪项只活在提示词里，哪项在适配时不可逆地丢失。

先把比较对象放在同一张坐标纸上

源码实现 Narrative Forge 本地固定提交 24c3c47 的核心对象是一个可编辑项目：互动模式保存带 choices 的镜头图，短剧模式保存 episodes[].scenes[] 的线性镜头；同一项目还能直接发起图像、视频和导出任务。核对入口是 static/src/project-model.js、static/src/draft.js、static/src/api.js、app.py 与 backend/route_registry.py。

源码实现 shuohao-skills 固定提交 4322897 的五个确定性脚本分别消费和产出 outline.json、cast.json、art.json、script.json、storyboard.json；脚本负责 seed、validate、render 和 export。文档声明 语义创作由读过 SKILL.md 与 pass 文档的 agent 完成。核对入口是根 README.md、各 skill 的 SKILL.md、references/schema.md 与 scripts/*.mjs。

逐层矩阵：同一个问题，两种保存方式

表中“现状”只描述冻结提交；“代价”是从这些实现推导出的信息损失，不等同于原作者承诺。路径均相对于各自仓库根目录。

表 1　从故事输入到最终输出的逐层比较
层／问题 Narrative Forge shuohao-skills 保留与损失
故事输入 源码实现 表单保存片名、梗概、类型、视觉风格、角色卡与场景卡；文本生成直接消费这些当前值。见 project-model.js 的 readMetaFromForm() 与 draft.js。 文档声明 novel-outline 从小说文本与总集数、单集时长、题材、改编幅度开始，并要求关键保留取舍附原文证据。见 skills/novel-outline/SKILL.md。 分析推论 前者适合已经压缩成项目简报的故事；后者保留较长的改编交接链。Narrative Forge 项目没有原文引用模型，shuohao 的来源证据也主要集中在大纲层，尚不是通用 provenance 图。
形式契约 源码实现 meta.mode 区分互动与短剧，并保存画幅、树深、分支数、每节点镜头数、集数和每集镜头数。见 state.js、project-model.js 与 draftRequestMeta()。 源码实现 五阶段 schema 围绕线性 AI 短剧：大纲规定集数与时长，剧本保存逐集 targetSeconds，分镜再量化 segment 与 cut。见 outline、script、storyboard 的 schema 与校验器。 分析推论 Narrative Forge 原生表达两种观看结构，但互动生成器偏向固定深度的满树；shuohao 的线性边界更窄，却让时长和交付责任更明确。
戏剧场次 源码实现 UI 与项目 JSON 中名为 scene 的对象实际是一条镜头记录；地点另由 sceneCards 表达，没有独立 DramaticScene 实体。见 createScene()、scene-list.js 与 draft.js。 源码实现 script.json 保存集内场次出现与 flow；其中 sceneId 引用 art.json 的地点资产，而 storyboard 用集内 sceneIndex 回指场次出现。见 script 与 storyboard schema。 分析推论 shuohao 比前者多保留了“场次 → 节拍”，但场次出现仍没有稳定 ID；相同地点多次出现时，sceneId 不能单独回答“是哪一场戏”。
Beat／Shot 源码实现 短剧提示要求模型先“内部拆拍”再返回 scenes，安装后只留下镜头动作、对白、景别、时长和首尾状态；互动多镜节点用 storyNodeKey 分组。见 generateSerialDraft() 与 expandInteractiveStoryScenes()。 源码实现 script.flow 保存动作或台词 beat；每个 storyboard cut 用 beats: [起, 止] 认领连续位置区间，segment 包含多个 cut。见 novel-storyboard.mjs 的 coverage gate。 分析推论 Narrative Forge 丢失显式 beat；shuohao 保留覆盖但使用位置索引，并要求每拍恰好归一个 cut。插入节拍会使索引漂移，多机位安全覆盖也无法原生表达。
互动与汇流 源码实现 镜头可携 choices[].targetSceneId 与 nextSceneId，播放器按目标 ID 跳转；生成结果安装器检查重复 key 和无效选择目标。见 story-graph.js、player.js、installGeneratedStory()。 源码实现 outline、script 与 storyboard 的冻结 schema 都是按集顺序组织，不含选择边、条件或分支汇流状态。 分析推论 互动是 Narrative Forge 的明确强项；但现有数据没有把选择条件、状态变量与汇流兼容规则独立建模，合法目标 ID 不等于叙事图一定可达、可终止或可汇流。
提示词 源码实现 每镜保存 imagePrompt 与 videoPrompt；prompt.js 可从镜头、角色卡、场景卡和连续性字段重新组合，但组合结果也被写回项目。 源码实现 每个 cut 保存关键帧 frame，每个 segment 保存供应商导向的 h3Prompt；校验器逐字核对对齐首行、切点时刻、台词与运镜。见 storyboard schema 与 h3AlignmentLine()。 分析推论 两者都把派生提示持久化，因此人工微调方便；代价是来源规格与编译结果可能漂移。shuohao 的门能发现部分漂移，但 H3 协议进入主文档，供应商耦合更显式。
媒体与任务 源码实现 api.js 创建可停止或恢复本地等待的图像／视频任务、轮询 prediction、保存状态与本地路径；停止不会调用供应商取消接口。app.py 代理供应商、保存资产并异步导出试玩包或分集包。 文档声明 分镜 skill 可选调用当前 agent 的图像能力生成关键帧，但明确不执行视频生成或剪辑；export 只写每段 prompt.md、图片槽位与 manifest.json。 分析推论 Narrative Forge 更接近可执行工作台；shuohao 更接近生产规格编译器。前者的任务状态嵌在镜头对象，后者的生成任务本身没有一等记录。
校验 测试约束 前后端测试覆盖启动、项目读写、供应商秘密、媒体参数、导出与部分草稿安装；生成结果安装器还限制重复 key、目标引用与规模。见 static/src/*.test.js、backend/test_server.py。 测试约束 五个 selftest.mjs 用击穿夹具保护各层确定性逻辑；storyboard 进一步检查 exact-once beat 覆盖、时长链、引用和 H3 对账，第 17 道 shot-recipe 门仅在挂载卡库时启用。 分析推论 shuohao 的跨层确定性门更强；Narrative Forge 的真实媒体与导出路径更完整。两者的测试都不能证明镜头节奏、表演或构图已经好看。
持久化 源码实现 浏览器用 localStorage 保存当前项目与一次覆盖恢复快照；POST /api/save-project 原子写入 projects/<title>/project.json 并把旧文件复制到时间戳备份目录，媒体另存项目资产目录。 源码实现 每层以独立 JSON 为主数据，Markdown／HTML 可重渲染；storyboard export 写段目录与 manifest，validate/checkup 把门结果追加到工作目录的 .gates.jsonl。 分析推论 前者适合单项目连续操作，后者适合文件式审阅和 Git 对比。两者都缺少跨实体事务、并发冲突和细粒度人工批准模型。
版本与可追溯 源码实现 normalizeProject() 把项目结构版本写为 6，服务器保留项目文件备份；单个镜头、提示词、人工修改和生成结果没有各自的版本链或来源边。 源码实现 各 SKILL.md 有 skill 版本，JSON 有 source，门日志有运行时间与文件名；业务 JSON 本身没有统一 schemaVersion、实体 revision 或上游内容哈希。 分析推论 “能找回旧文件”与“能解释某个画面为何如此”不是一回事。两边都还无法完整回答：哪个人工批准版本，经哪个适配器，生成了这个具体文件？
最终输出 源码实现 可保存项目 JSON 与素材，并通过后台 job 生成互动试玩包或短剧分集成片包；互动和短剧导出是两条不同端点。见 export_player()、export_serial()。 源码实现 五阶段输出 JSON、Markdown、单页报告；storyboard 另导出 H3 提示文件、切点 manifest 与关键帧槽位，不合成最终视频。 分析推论 前者交出可播放候选，后者交出可复核制作包。选择哪一个取决于你需要“立即运行”还是“逐层审计”，并非输出文件越多越成熟。

强项来自边界，弱项也来自同一个边界

Narrative Forge：短反馈回路

分析推论 它最有价值的不是某条提示词，而是从镜头编辑、参考图、生成任务到播放器／导出的短回路。需要快速验证互动路线或逐镜媒体结果时，集中式项目状态减少了文件搬运。

分析推论 代价：故事节点、场次、节拍、镜头和任务挤在少数对象里；越往大型项目、多人协作和重新生成发展，越难判断一次修改影响了什么。

shuohao：显式交接与质量门

分析推论 它最有价值的是每一阶段都能单独 seed、审阅、validate 和 render。长篇小说改编、批量分集和稳定资产 ID 需要大量对账时，这种文件契约比一份不断膨胀的项目对象更容易诊断。

分析推论 代价：流程面向线性短剧并深度绑定位置索引与 H3 投产格式；没有持久任务、分支状态或成片执行层，跨阶段修改仍依赖操作者重跑正确命令。

共同缺口：来源、批准与派生没有闭环

分析推论 两者都能保存“现在是什么”，却不能系统回答“谁在何时批准了哪个来源版本”“哪些字段是人工决定”“哪些提示和媒体因上游修改而失效”。这不是多加一个时间戳可以解决的问题。

私有能力不能用想象补齐

文档声明 shuohao 的 docs/superpowers/specs/2026-08-21-shot-recipes-repository-migration-design.md 称完整 shot-recipes 卡库已移至私有仓库；公开提交只有挂载接口、迁移说明与最小测试夹具。

分析推论 因而不能把未审计卡库算作公开系统的完整镜头知识，也不能据此贬低或拔高现有质量门。

什么时候选哪一种，什么时候不该二选一

快速做出可玩的互动原型

分析推论 优先利用 Narrative Forge 的剧情边、播放器、媒体任务和试玩导出；同时把复杂条件与汇流状态另存，不要假设满树生成器就是最终叙事模型。

从长篇材料批量改编线性短剧

分析推论 优先利用 shuohao 的阶段 JSON、稳定 C/S/P 资产 ID、时长对账和质量门；同时尽早替换场次与 beat 的位置索引，避免中途插入导致全链漂移。

要长期维护自己的生产系统

分析推论 不要简单把一个仓库塞进另一个。保留 Narrative Forge 的短执行回路与 shuohao 的显式契约，把两者接到供应商无关的规范领域模型上。

只需一次性教学或概念验证

分析推论 选择更短的路径即可。规范模型的价值来自变化、重跑和协作；若没有这些成本，过早建设完整平台反而会淹没创作问题。

本章结论

分析推论 Narrative Forge 的优势是执行闭环，shuohao 的优势是交接契约。前者容易把叙事层压进镜头与项目状态，后者容易把通用导演意图压进线性位置索引与特定视频协议。重构建议 重建时不应复制两边所有字段，而应先保存那些一旦丢失就无法可靠重算的创作决定，再把按钮、报告、提示与任务当成可替换的消费端。

冻结证据：Narrative Forge 24c3c47 的 static/src/project-model.js、draft.js、prompt.js、api.js、player.js、app.py、backend/test_server.py；shuohao-skills 4322897 的根 README.md、五个 SKILL.md、各 references/schema.md、scripts/*.mjs、selftest.mjs 与 shot-recipes 迁移设计。完整私有 shot-recipes 卡库不在已审计范围。
