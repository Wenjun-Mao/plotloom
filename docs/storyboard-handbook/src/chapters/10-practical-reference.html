读代码、改流程、验收分镜

这一章不是让你真的拿纸笔完成整套制作，而是把前面的知识压成一套可重复查询的方法：拿到任何故事生成项目时，知道先问什么、沿哪里追代码、哪些产物应该存在，以及什么情况下可以修改、应该重构或值得重写。

一、理解第三方系统的四遍阅读法

不要从文件树第一行一直读到最后一行。每一遍只追一种问题，读完都应留下一个可以验证的产物。

第一遍：用户动作

从一个真实按钮或命令开始，追到它产生的最终文件、页面或媒体任务。

  • 入口是什么？
  • 中途跨过哪些模块或进程？
  • 失败会在哪里暴露？

留下：一张端到端调用图。

第二遍：数据生命史

选择一个概念，例如“场次”或“镜头”，追踪它从输入、内存、持久化到导出的每次变形。

  • 何处获得 ID？
  • 哪些字段是创作者输入？
  • 哪些字段会被重新计算或静默丢弃？

留下：一张字段转换表。

第三遍：失败契约

读校验器、测试和回退逻辑，而不是只读成功路径。

  • 什么输入会被拒绝？
  • 什么错误会被默认值掩盖？
  • 测试保护的是格式、行为还是创作质量？

留下：一张失败模式清单。

第四遍：可替换边界

假设更换文本模型、视频模型、存储或前端，观察哪些数据仍然成立。

  • 核心事实是否混在提示词里？
  • 供应商参数能否由通用规格派生？
  • 人工修订能否跨重新生成保留？

留下：一张重构接缝图。

每次都用同一个小案例

用“月城控制室”这样的短场景做探针，比直接输入一部长篇更容易看清信息在何处丢失。探针应同时包含空间、道具、反应、短对白、连续状态和一个形式差异；这样一轮运行就能触碰多数关键契约。

重构建议 同一个词在电影制作、Narrative Forge、shuohao 和你未来的系统中可能代表不同对象。下表是本手册建议长期采用的工作词典，不是两个仓库已经共享的 schema；比较时先回到工作定义，再看具体实现。

五、先判断问题在哪一层，再决定怎么改

第三方项目最容易出现的维护错误，是在最靠近症状的地方加条件。先判断失败的是故事、领域契约、适配器还是界面，才能把修复放到真正拥有该规则的层。

只改配置

适用：模型地址、时长上限、提示语言或安全部署参数发生变化，但通用故事与镜头契约没变。

警报：为了新供应商去改故事字段或镜头语义，说明适配边界不存在。

改适配器

适用：通用的 5 秒镜头需要映射到供应商六档时长，或同一关键帧需要不同上传协议。

警报：适配器开始决定人物做什么、哪条分支成立，说明它越权进入创作层。

改领域模型

适用：无法表达一个节拍被多个镜头覆盖、同一地点出现于多场戏、分支汇流或人工覆盖来源。

警报：只往自由文本里补标签，会延迟而不是解决结构缺口。

改工作流

适用：系统在场次未批准前就生成昂贵视频，或每次改台词都必须重做不相关资产。

警报：增加更多按钮，却没有定义批准点、失效传播和恢复路径。

渐进重构

分析推论 适用：经真实使用证据确认，现有界面、媒体任务和导出仍有价值；可以在旁边建立规范模型与双向格式转换器。

前提：能写出兼容测试，并允许一段时间内新旧表示并存；但任一功能在任一时刻只能有一个写入权威，另一侧只做只读投影与差异观察。

完全重写

适用：核心对象无法表达目标产品、状态变化难以迁移，且保留旧架构的成本高于重建。

前提：先冻结行为样本、数据迁移和验收标准；“代码不好看”本身不构成重写理由。

六、怎样判断自己已经真正理解

“我能读懂代码”还不够。达到下面四级，才从会使用走到有能力重建。

  1. 能解释 不用仓库术语，向另一个人解释粗梗概如何变成场、节拍、镜头、画格和生成任务，并说明每层为什么存在。
  2. 能追踪 任选一个镜头，从 UI 或 JSON 追到提示、请求、任务、文件和回读状态；能指出中间每次字段改名与信息损失。
  3. 能预测 在运行前预测：删掉一个 beat、改变一个供应商时长或插入一个互动汇流节点，会使哪些产物失效、哪些不应重算。
  4. 能替换 把文本模型、媒体供应商或存储实现换掉，而不改故事事实和导演母版；适配结果可以重新生成，人工批准不会消失。

一个很实用的闭卷测试

关掉仓库，只看《月城失物局》中“月城控制室”这场戏的粗梗概。尝试口头重建：SC-03 与 SC-08 为什么是两场戏；九拍为什么变成八镜；镜 08 的线性与互动版本究竟在哪一层分叉；29 秒进入两套系统后为什么会变形。能把这些因果讲清，再回到代码验证，你学到的才不是文件路径记忆。

七、以后拿到任何生成式影视仓库，先问这十二题

  1. 系统把来源故事和模型补写的内容分开保存了吗？
  2. 故事节点、戏剧场次、地点资产和镜头是独立对象吗？
  3. 节拍到镜头是一对一，还是能表达多对多覆盖？
  4. 线性后继、互动选择和分支汇流由哪一层拥有？
  5. 每个镜头的入口／出口状态能否机械检查？
  6. 时长是导演决定、估算、供应商枚举还是媒体实测？
  7. 提示词能否从规范数据和资产引用重新编译？
  8. 人工修改会不会被下一次生成静默覆盖？
  9. 模型返回格式与长期项目格式是否明确区分？
  10. 失败时能否定位到具体对象、字段和来源版本？
  11. 更换供应商是否只影响适配器与任务，而不是故事主数据？
  12. 仓库实际执行了什么，又有哪些只是 README 或提示词中的承诺？

彻底理解一个生成系统，不是知道每个按钮调用了哪个函数，而是能解释：哪些决定来自故事，哪些由导演新增，哪些只是供应商要求；它们怎样被保存、验证、转换、执行，又怎样在修改后可靠地重新计算。
